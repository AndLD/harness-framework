Added: a flow setting `orchestratorLimits.context` (50% of the orchestrator's window by default, beside `reuseLimits`) and a handoff entry in the flow's log (`### … — handoff: <why>` with State, Decisions, Next step, Waiting for), which `harness flow check` holds; `harness flow status` and `dispatch` print the orchestrator's context against the limit (`--orchestrator <percent>` feeds a reading back; a runtime that cannot read it leaves the judgment to the orchestrator), and `dispatch` prints a cache hint (how long the previous worker's prompt cache still lives, and that a start past it is logged cold). The procedure `run-flow` (step 9) and the runtime contract's `context` role say so (a change of their meaning, decided as `contract.change`). Nothing is required of a project: a flow without the setting takes the default; to give an existing flow the setting, add `"orchestratorLimits": { "context": 50 }` to its settings block (the flow template has it).
