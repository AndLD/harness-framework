Fixed: a worker that a flow starts on the command line is no longer left refused every edit and command. A `claude -p` worker has no one to answer a permission prompt, so under the default mode it could not write a file or run Git, and reported itself blocked. The flow settings gain `permissions` (`{ "mode": "<a mode of the runtime>", "allow": ["<a tool by name>"] }`, in the runtime's own words, absent by default); the runtime contract passes it to an executor's `start` and `continue`, the Claude Code preset turns it into `--permission-mode` and `--allowedTools`, `harness flow dispatch` prints what a worker will be allowed (and warns when nothing is set), `harness flow check` checks the setting, and the procedure `run-flow` says that the choice is the owner's. A session that the desktop app starts runs under the app's own permission settings and is not affected. A local runtime adapter may add an optional `permissions` operation to an executor; nothing is required of a project.
