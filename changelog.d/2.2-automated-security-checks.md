Added: `harness check security`, the probes of the security review that a script can decide (14 of the 28 scriptable ones, each finding starts with its probe id, and the result lists the rest as the gaps for the next review): a secret scan of the tracked files with the new profile role `security.secretPatterns` (nine default rules, no download, a finding never prints the value) and of the lines a history range added (`--range <a>..<b>`); tracked files that match `access.denyRead`; a lock file beside each manifest, open versions and tracked binaries; the host's workflow files (permissions declared, actions pinned to a commit, no event text spliced into a script, no `pull_request_target` that checks out the proposed code); the runtime's committed settings (the deny rules, no bypass of the permission checks, no broad allow rule: a bare tool, an edit outside a named folder of the project or inside the settings, the hooks or Git, an interpreter, package runner or fetcher with any argument); and, with `--audit`, the dependency audit (the new stack role `dependency-audit` and the role `commands.audit`). The adapters gain the optional roles `dependency-audit` (node-ts, python), `ci-audit` (github) and `settings-audit` (claude-code). A project does nothing: `harness check all` runs the check only after `checks.security` is set to `true` in the profile file, which the owner does when the project passes it; `security.exclude` names test fixtures with a planted defect and `security.allowedRules` the broad allow rules a project accepts. The `.gitignore` of a new project also lists `*.pem` and `*.key`, as `access.denyRead` does; an existing project adds the two lines.
