Added: a flow may drive steps in another repository. A flow still belongs to its home repository; its `repos` setting may name external ones, each a row `{ "remote": "<owner>/<name>", "role": "consumer", "kinds": ["consumer-take"] }` under an alias that a new optional `Repo` column of the steps table uses (the flow template now leaves the column out: with the home repository only, every step is the home repository's). The folders on this machine go in the ignored `harness-profile.local.json` (`repos.<alias>`). In an external repository the orchestrator only starts a worker (in that folder; the manual executor when it is not set): it edits nothing there, the prompt sends the worker to that repository's own entry file, a release cut and the answers to reports stay the home repository's, and a step there names the work by what it does ("take `1.0.0`"), never by task ids (`harness flow check` refuses an id, a kind that is not `consumer-take` or `custom`, and a bad row). `harness flow status` checks such a step through the host: the lock file the repository holds and its pull requests that mention the version. The host contract gains the optional role `remote-state` (`remoteFile`, `remotePullRequests`; the GitHub preset reads them with `gh`). Changed: the `repos` setting of a flow was a map of aliases to paths, which nothing used yet; an alias is now a row (a path there is refused), and the home repository is implicit. A project that has no flow of its own yet has nothing to do.
