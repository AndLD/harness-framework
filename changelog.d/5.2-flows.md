Added: flows, files of the plan that an orchestrator runs. A project that has a releases file can name a folder in the new optional profile role `paths.flows` (by default `docs/development-plan/flows`): one file `flow-<n>-<slug>.md` per flow (an ordered chain of steps that delivers one or more releases, with a settings block — `mode` brainstorm or seamless, `askAt`, `levels`, `executor`, `reuse`, `commits`, `usage`, `repos` — and a steps table) and its log beside it, from the new templates `core/plan/flow-template.md` and `core/plan/flow-log-template.md`. `harness plan summary` creates the folder's index, writes its table from the flow files and links it from the releases block of the plan index; its check refuses a release that two flows declare or that the releases file lacks. The new procedure `run-flow` (a skill too) says how an orchestrator runs a flow: decision levels D0 to D4, the hard limits no mode crosses, the step report a worker ends with, the unbiased analysis, escalation and digests (plan method, section 10). The resume phrases may name flows ("Run flow N", "Run flows N–M", "Continue flow N"): add them to `plan.resumePhrases` of the profile file if the project uses flows. The Git rules let a flow's phrase approve only what its settings allow, never a merge or an answer they keep for the owner. A project without the role changes nothing.
