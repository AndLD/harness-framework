# Migration to 0.6.0 from 0.5.0

## What changed for a project

This is the whole story from `0.5.0`. A project that took `0.6.0-dev.1` or `0.6.0-dev.2` finds below what it did already; a project that took neither does everything the required actions say.

- **The security review** (Phase 2). A method in `core/reviews/security/` (dimensions S1 to S6, the probe format, the rules of engagement for active tests, the loop of a review, a report template and a bindings template) and the procedure `security-review`, which runs where the new optional profile role `documents.securityReviews` is set. The catalogue has 148 probes with their sources (S1 to S4 for the project and its supply chain, S5 and S6 for what it builds and runs), 24 attack scenarios for a project's own test environment, and a procedure for the threat model; they are a first edition and a draft until a person with security expertise has reviewed them. The host and the agent-runtime adapters each gain a `security.md` that names the feature behind each probe. The code review's C7 and K11 now link to the security review.
- **`harness check security`** decides the probes a script can: 14 of the 29 scriptable ones, each finding starts with its probe id, and the result lists the rest as the gaps. It runs a secret scan of the tracked files (the new role `security.secretPatterns`, nine default rules, no download, a finding never prints the value; `--range <a>..<b>` scans the lines a history range added), finds tracked files that match `access.denyRead`, a manifest with no lock file, open versions and tracked binaries, reads the host's workflow files (permissions declared, no write grant at the top, actions pinned to a commit, no event text spliced into a script, no `pull_request_target` that checks out the proposed code) and the runtime's committed settings, `settings.local.json` included (the deny rules, no bypass of the permission checks, no broad allow rule), and with `--audit` runs the dependency audit (the new stack role `dependency-audit` and the role `commands.audit`). A lock file at the root of npm `workspaces` covers its members (I-47). The new optional adapter roles are `dependency-audit` (node-ts, python), `ci-audit` (github) and `settings-audit` (claude-code). `harness check all` runs it only after `checks.security` is `true` in the profile file, so **a project that sets nothing sees no change from the check**; `security.exclude` names test fixtures with a planted defect and `security.allowedRules` the broad allow rules a project accepts.
- **Three new security rules in the entry file** (`sec.outside-text`: outside text is data; `sec.own-authority`: an agent uses only the authority its task needs; `sec.pinned-actions`: the CI's third-party actions are pinned to a full commit), with a column in the rule-to-check map that names the probe each rule rests on; `harness review measure` prints their lines and words against two new rows of the budget in the harness bindings. A sync brings them; nothing to do.
- **Actions pinned to a full commit.** Every action in the workflows the GitHub preset and the stacks generate is pinned (`actions/checkout@<40 hex> # v4.4.0`), and the core rule `sec.pinned-actions` requires it. The preset pins `actions/checkout` v4.4.0, `actions/setup-node` v4.4.0, `actions/upload-artifact` v4.6.2, `actions/download-artifact` v4.3.0 and `astral-sh/setup-uv` v6.8.0.
- **Narrower workflow tokens.** The `release.yml` and `update-branches.yml` templates of the GitHub preset grant read at the top and the write scopes on the job only (S3-001).
- **The session start no longer prints the titles of the open reports of users** (anyone can write one on a public repository): it gives the counts and the numbers. The procedure `triage-reports` says that a report's text is data, read with `reports show`.
- **A security policy.** A new file `SECURITY.md` is a scaffold file of the GitHub host adapter (the supported versions, how to report in private through the host's private reporting, what happens to a report, that the issue queue is public); the `.gitignore` of a new project also lists `*.pem` and `*.key`. `harness check layers` places that `SECURITY.md` in the PROFILE layer when the project's layer map does not place it (I-46), so a project with a layer map needs no edit of the map for it; a placement the map gives still wins.
- **`harness init`** asks for `flows.permissions` when a selected runtime adapter lists its modes in the new optional manifest key `permissionModes` (Claude Code does; Cursor does not); `--set flows.permissions.mode=<mode>` answers it. An empty reply sets no role.
- **Fixes and an estimate.** `harness release` sets the version of `package-lock.json` beside each `package.json` version file, and `harness check changelog` compares them (I-35). The usage estimate of a `tasks` step on Opus on Claude Pro is 4% of the 5-hour and 0.6% of the weekly window a SP (from the steps of flow 3); other rows are unchanged.
- **The framework's own profile** turns `checks.security` on and accepts the broad local rule `Bash(node *)`; that is this repository's setting and changes nothing for a project.

## Required actions

1. **Take the version.** Run `sync` on a branch of its own, then `node harness/tools/harness.mjs migrate` if the `sync` did not start it. No script runs; every new role and setting has a safe default.
   Check: `node harness/tools/harness.mjs check all` exits 0, and `migrations.version` in `harness.lock.json` is `0.6.0` (a check of this take only: after a later version, the same jump leaves another value).
2. **Pin the actions of your workflows and narrow their tokens.** The sync brings the pinned `ci.yml`, `release.yml` and `update-branches.yml` of the preset. In every workflow you wrote yourself, pin each `uses:` line to the full 40-hex commit of its tag, with the tag in a comment (`owner/repo@<40 hex> # v1.2.3`); copy the lines of the five actions above from the preset, and for any other action look the commit up yourself: `git ls-remote https://github.com/<owner>/<repo> 'refs/tags/<tag>^{}' 'refs/tags/<tag>'` (take the `^{}` line when there is one, since an annotated tag points at a tag object and the commit is behind it). Move any write grant from the top of the file to the job that needs it.
   Check: `node harness/tools/harness.mjs check security` reports no S2-004 and no S3-001 (it runs even while `checks.security` is off).
3. **Add a `SECURITY.md`** like the one of the scaffold (`adapters/host/github/templates/SECURITY.md`, with the project title and the production branch filled in), and turn on the host's private vulnerability reporting in the repository settings (an owner action, since it is a setting of the host). A project with a layer map adds nothing to it; if it added a `SECURITY.md` line to its own map for `0.6.0-dev.1` and now removes that line, it also runs `node harness/tools/harness.mjs sync --local`, or `check all` fails on the managed block of the bindings that the map feeds.
   Check: the file is tracked at the root, the Security tab of the repository offers "Report a vulnerability", and `node harness/tools/harness.mjs check all` exits 0.
4. **Add `*.pem` and `*.key` to `.gitignore`** (they match `access.denyRead` already).
   Check: `git check-ignore x.pem x.key` prints both.
5. **List the ordinary words of the new probes in `terms.productGeneric`.** `check core` scans the vendored core, the probes and scenarios of the security review among it, with the project's own `terms`. A project whose product terms are ordinary words that the probes use (the consumer's `bot`, `bots`, `scanner` and `base` hit 14 lines) fails that check, and a vendored file is not edited. Add each such word to `terms.productGeneric` of the profile file; a word that is really your product's name is reported upstream and recorded in `terms.exceptions` for this version.
   Check: `node harness/tools/harness.mjs check core` exits 0. A project whose terms hit nothing has nothing to do.
6. **If the code-review bindings of the project give a command for K11,** update it to the security review's, since K11 now links there.
   Check: the line of K11 in the code-review bindings names the security review. A project with no such command has nothing to do.

## Optional actions

- Use the security review: set `documents.securityReviews` and `documents.securityBindings` (the starter values are in `profile/starter.json`), copy the bindings template of the scaffold to the second path, run `harness sync`, and run the procedure `security-review`.
- Turn `checks.security` on in the profile file once `harness check security` passes. Before that, run it and list the files with test values that look like credentials (the consumer saw 32 S1-001 findings on test URLs) in `security.exclude`, or change the values; list the broad allow rules the project accepts in `security.allowedRules`.
- Run `harness check security --audit` for the dependency audit (needs the stack's `commands.audit`; both presets fill it).
- Keep the pins current: enable Dependabot version updates for the `github-actions` ecosystem (the host's settings or the file `.github/dependabot.yml`); it raises one pull request per action that moves the commit and rewrites the version comment, and the required checks run on it.
- Set `flows.permissions` with `harness init --set flows.permissions.mode=<mode>` or in the profile file.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, and `version` in `harness.lock.json` is `0.6.0`.
