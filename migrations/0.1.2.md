# Migration to 0.1.2 from 0.1.1

## What changed for a project

- **The Git guard judges a command by the repository it acts on** (3.17). `guard-shell` follows a `cd` before a Git command (a `cd` inside parentheses ends with them), `-C`, `--git-dir` and the variables `GIT_DIR`, and judges the commit or push by the branch of that repository, not by the branch of the project directory. A repository it cannot resolve (an unknown directory, a variable, `--work-tree` alone) counts as protected. It changes nothing you configure.
- **Auto-merge** (3.18). Where the host protects the branches, an agent now enables the host's auto-merge (squash) on the task and plan-related pull requests it may merge without asking, as the last step of a task, so that the host merges them once the required checks pass. The guard refuses `gh pr merge --auto` into the production branch, on a release or hotfix branch, on a pull request not into the integration branch, and wherever the new profile switch `host.autoMerge` is off. The switch is on where `host.protection` is `true` and off where it is `false`; setting it to `false` brings back the old rule (the agent asks before it merges and never enables auto-merge unasked).
- **The host setup** (3.18). `harness host protect` also turns on the repository setting "allow auto-merge" (and keeps "delete head branches" off). The GitHub adapter has a workflow, `update-branches.yml`, that brings the integration branch into every open pull request waiting on auto-merge when the integration branch moves (the ruleset requires a pull request to be up to date), and `ci.yml` gets the trigger `workflow_dispatch`. The bootstrap asks the host what it offers and sets `host.protection` and the files; `--no-host-setup` skips it.
- **`harness branch update [--previous <branch>]`** (3.18) merges the integration branch into the branch of a task stacked on the previous task's branch, after the squash merge of the previous pull request, and resolves the conflicts that only that squash causes.
- **The core rules** about merging, waiting and stacking changed (`agent.auto-merge`, `agent.stack`, `agent.ci-fixes`); the procedures `open-pull-request` and `end-session` say how a pull request ends and what the last message lists.
- **The bootstrap fills `repository.url`** (3.1) from the host adapter's new optional role `repository-address`, so a new project's changelog links are real. A project that was bootstrapped before has no address if it never set one: add `repository.url` to the profile file (the web address of the repository) before your next release.

## Required actions

1. **Regenerate the managed files.** The rules of the entry file and two procedures changed, and a sync generates with the tools of the version you leave.
   Run `node harness/tools/harness.mjs sync --local`.
   Check: `node harness/tools/harness.mjs check generated` exits 0.
2. **Decide on auto-merge.** With `host.protection: true` it is on by default. To keep the old behaviour, set `host.autoMerge` to `false` in the profile file and run `sync --local` again; then you are done with this step. To use it:
   - Run `node harness/tools/harness.mjs host protect` again as an administrator of the repository (a setting of the host is not a file, so no script can do it for you).
     Check: `gh api repos/<owner>/<name> --jq .allow_auto_merge` prints `true`, and `.delete_branch_on_merge` prints `false`.
   - Add the workflow that keeps the pull requests waiting on auto-merge up to date: copy `harness/adapters/host/github/templates/update-branches.yml` to `.github/workflows/update-branches.yml`, replacing `<%= branches.integration %>` and `<%= branches.production %>` with the names of your branches, and add `workflow_dispatch:` under `on:` in `.github/workflows/ci.yml` (the template `harness/adapters/host/github/templates/ci.yml` shows where). If your CI does not start on a push made with the default token, add a secret `AUTO_MERGE_TOKEN` (a token of your own) so that the host starts the checks itself.
     Check: `node harness/tools/harness.mjs check values` exits 0.

## Optional actions

- Set `repository.url` in your profile file if it has none (see above): `harness release` writes it into the compare and tag links of the changelog.
- Remove from your own project rules (the project-specific section of the entry file) a standing request for auto-merge, if you wrote one: the core rule repeats it now.
- A task that needs the previous one can branch from its branch (one level) while that pull request is open; after the squash merge, `node harness/tools/harness.mjs branch update --previous <that branch>` brings in the integration branch.

## How to verify

`node harness/tools/harness.mjs check all` exits 0, and `version` in `harness.lock.json` is `0.1.2`.
