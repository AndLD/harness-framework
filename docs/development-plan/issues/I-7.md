# I-7 — `harness branch update` left merge conflict markers in a file it reported as resolved, and no check refuses them

**Status:** ⬜ · **Agent:** C1 · **Size:** 2 SP · **Area:** Git rules · **Reported:** —

**`harness branch update` left merge conflict markers in a file it reported as resolved, and no check refuses them**: after the squash merge of task 3.20, `harness branch update --previous feature/3.20-backlog-queue` on the branch of B-1 (pull request #74) said "Resolved to feature/B-1-probe-switch's side" for `docs/development-plan/backlog/B-1.md` and `archived/B-1.md` (the item was moved to the archive on this branch and edited on the other). The file that was committed and merged into `develop` held `<<<<<<<< HEAD:…`, `========` and `>>>>>>>> origin/develop:…` lines (eight characters each, not Git's seven) around two copies of the item's header, and `npm run docs:check`, the pull request's checks and the review did not notice, because nothing looks for them. It was found when task 3.21 read the file. Fixed by hand in 3.21 (the header of B-1 rewritten); the defect is still in the tool and in the checks. A fix reproduces the case (a file moved on one side and edited on the other, resolved to one side), makes the resolution leave no marker or stops and says which file is left to resolve, and adds a check (`check links`, `check plan` or a check of its own) that fails on a line of 7 or more `<`, `=` or `>` characters at the start of a line in a tracked Markdown or JSON file. Found by the agent of task 3.21.
