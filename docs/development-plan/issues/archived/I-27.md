# I-27 — A project cannot give its flows a default for the workers' permissions

**Status:** ✅ · **Agent:** C2 · **Size:** 2 SP · **Area:** plan format · **Reported:** —

**A project cannot give its flows a default for the workers' permissions**: the flow setting `permissions` (`{ "mode", "allow" }`, in the runtime's own words) is absent by default, so a new flow's workers start in the runtime's strictest mode and are refused, or ask the owner for, almost every command, until each flow's file sets the mode again (flows 2, 3 and 4 of this repository set `auto` by hand; in flow 2 the mode `acceptEdits` asked the owner for almost every command of a worker). The owner asked (2026-11-07) that the mode `auto` be the default of the flows to come. The core cannot name a mode (it is a word of the runtime, and the runtime contract says that an adapter never chooses one, since what a worker may do is the owner's decision), so the default belongs to the project: a new optional profile role (for one, `flows.permissions`, the same shape as the setting) that a flow without its own `permissions` takes; the flow's own setting wins. This repository sets it to `{ "mode": "auto", "allow": [the six tools of flow 2] }`. A fix: the role in the profile schema and the document of roles, `harness flow` (dispatch, check, prompt) reading it under a flow's own setting, the text of the plan's README and of the runtime contract ("absent by default" becomes "the project's default, else absent"), the bootstrap question for a project on a runtime whose adapter has such a mode, a changelog fragment; verified by tests of a flow without the setting on a profile with and without the role.
