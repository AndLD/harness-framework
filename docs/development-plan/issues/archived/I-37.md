# I-37 — The security review's method and checks, corrected from the first review

**Status:** ✅ · **Agent:** C2 · **Size:** 2 SP · **Area:** review method · **Reported:** the [first security review](../../../quality-reviews/security/2026-11-08.md), section 9

**The security review's method and checks, corrected from the first review**: the first review of the framework (task 2.4) found where the method and the checks fall short.

- `check security`, S3-001: the check accepts any declared `permissions:`. Make it follow the probe: read-only at the top, write on the job.
- `check security`, S4-002 and S4-023: the runtime's `settings-audit` reads the shared settings only. Read the local file too.
- `check security`: a result with findings does not list the gaps, which step 4 of the method relies on. List them in every result.
- The catalogue: the trait `releases` does not separate a built artifact from a tag and notes, so S2-020 seems to apply where it cannot. Add a trait or a line to the probe.
- The method, section 4: it names the branch after the review date, and a review that is a plan task has its own branch. Say which wins.
- The catalogue: S3-016 is `manual`, and the scopes of the token in use can be read by a command. Split it, or note that part.
- The catalogue: add a scriptable companion of S4-011, which finds whether the context of a hook carries text from outside.
- The layer map: a project's first security report belongs to no layer until `layers` lists it, and only the push finds that (the check skips untracked files). The scaffold should list the reports of the security review as it lists those of the harness review, or the method should say so.
- The report template: add a place for the project traits that the reviewer decides (section 2 of the first report holds them today).

**Done when:** each item is changed or closed with a reason, the method's changelog has a line, and `node --test` and `harness check all` pass.
