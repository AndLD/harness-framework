### 2026-11-05 — the `permissions` setting of a flow, mapped by the executor
- **Branch:** `bugfix/I-11-worker-permissions` — from `develop`; the owner chose to fix it before the live run of flow 1 and to decide the mode themself ("Option A"), so it is also added to the `0.3.0` row of the releases file.
- **What was built:** (1) The flow setting `permissions` (`{ "mode": "<a mode of the runtime>", "allow": ["<a tool by name>"] }`, in the runtime's own words, **absent by default**), checked by `harness flow check`. (2) The runtime contract: `start` and `continue` take
  `permissions`, and an executor may have an optional `permissions` operation, one line of text saying what a worker will be allowed and what happens when nothing is set (the conformance suite holds it to returning text). (3) The Claude Code preset turns the
  setting into `--permission-mode` and `--allowedTools` on the command line, before `--output-format` (the tools flag takes every word after it, so the prompt would be swallowed otherwise); the desktop app's `start_session` takes none, the app's own permission
  settings apply. (4) `harness flow dispatch` prints a `Permissions:` line, and says plainly when none is set that a worker on the command line is refused every edit and command. (5) The procedure `run-flow` (step 4: tell the owner
  before starting such a worker; step 7: a worker refused permission is continued once only with a mode the owner's settings give, else the flow stops and asks), the plan method, the runtime contract, a changelog fragment.
- **Verified by:** tests of the means (the flags and their position, the continue, no flag without the setting, the one-line text), of dispatch (the setting reaches the means and the line is printed; a runtime without the operation prints none), of the check of the
  setting and of the conformance rule; `npm test`, `npm run test:coverage`, `npm run lint`, `npm run typecheck`, `npm run docs:check`. **A probe** with the command that `dispatch` printed for a scratch flow whose settings carry
  `"permissions": { "mode": "acceptEdits", "allow": ["Bash(ls *)"] }`: a Haiku worker on the command line wrote a file and ran the allowed `ls`, with no permission denial in its answer (the same worker without the setting was refused its `Write` in the probe of task 5.9).
- **Decisions / deviations from the plan:** (a) **No default mode.** Which mode a worker runs under is the owner's decision (an unsafe default such as `bypassPermissions` would let every worker do anything), so the setting is absent unless the flow sets it, and
  the only change in behaviour without it is that `dispatch` says the worker will be refused. (b) **Neither flow 1 nor flow 2 was given a `permissions` value**: that is the owner's choice and was asked for in the hand-over of task 5.9. (c) The setting is in the runtime's words
  (core names no runtime), so `harness flow check` only checks its shape, not the mode names.
- **Problems / blockers / findings:** none.
- **Next step:** the owner sets `permissions` in the settings of flow 1 (and of flow 2 when it runs), then "Run flow 1".
- **Verify with:** `npm test`, `npm run docs:check`, `node tools/harness.mjs flow dispatch 1 1`.
