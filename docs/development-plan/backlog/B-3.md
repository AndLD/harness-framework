# B-3 — A flow starts its workers as nested sessions, and logs why when it uses the command line

**Status:** Proposed · **Size:** 5 SP · **Area:** procedures · **Source:** owner

The owner asked (2026-11-05) that the next runs of flows start each step's worker as a session nested under the orchestrator's session, as the first steps of flow 1 did, so the owner can open and follow it in the desktop app, and that this cause no more permission prompts than the flow's mode (brainstorm or seamless) requires.

**What happened in flow 1** (from its log and the orchestrator's transcript): steps 1, 1 (second run), 1a and 1b ran as nested sessions. At step 1c the app refused the orchestrator to start a session on the turn that a worker's report began, and the owner started it from a card. At step 1d the worker had to run in the consumer's folder, which a proposal card cannot carry, and after the owner remarked that running `claude -p` was their rule in the repository, the orchestrator started 1d and 1e, and after the re-run of 1e as a session, steps 1f to 3, on the command line, each in a worktree under the flow's `permissions`. No file of the repository says that `claude -p` is a rule: the executor default of the procedure is `session`, and the log named the command line "the owner's usual way" only. A `claude -p` worker is not shown in the desktop app, and the flow's `permissions` setting applies to it alone.

**What was found by experiment** (2026-11-05, three read-only haiku sessions, one observation each, so read it as an indication and repeat it in the task):

- In this project, the app allowed a worker session to start from the follow-up turn that the end of another worker began, three times in a chain (the first from the owner's message).
- A start with another repository's folder (`cwd`, the consumer `bot-rts`) was denied by the app's auto mode classifier, without a reason; the proposal card cannot carry a folder either. So the steps that run in a consumer are the open problem.
- The orchestrator's session was in auto mode, and a started session inherits its permission mode or a lower one; the experiment's workers only read a file, so the prompts of a worker that runs `git`, `gh`, `npm` and `node` were not tested.

**What is wanted** (the proposal, not the design): the executor `session` is the default of every step in the home repository, and the procedure says that a worker started on the command line is a fallback for one step, logged as a decision with its reason, never carried to the next step by habit. For a step in another repository, the procedure and the dispatch say what the app allows (a start the owner asks for in the chat, or the command line) and the owner chooses once per flow, in its settings. The permission mode a worker starts in (the app's `permission_mode`) is decided by the flow's settings and logged, and what the flow's `permissions` allow is also given to a nested session by the means the runtime has (its mode and the project's allow rules), so a worker asks no more than a `claude -p` worker under the same settings. The owner's choices of 2026-11-05 are in B-2 and its task 2.6, which already let the plan's files be written without a prompt.
