### 2026-11-04 — a project has procedures of its own
- **Branch:** `feature/4.1-project-procedures` — done.
- **What was built:** (1) *The role.* `paths.procedures` in the profile schema: an optional folder of procedure files in the format of `core/procedures/`. (2) *Listing.* `listProjectProcedures(root, profile)` reads the folder (each procedure gets `source`, its path from the root; a project without the role or the folder has none), and `listAllProcedures` joins them to the framework's and refuses a name that both have. (3) *Skills.* `projectSkillGenerator` (`tools/lib/skills.mjs`) gives, for each selected runtime that packages procedures, the skill of each procedure of the project, as whole files through the `expand` form of a generator (items without `block` are now written as they are); the packaging of Claude Code and Cursor names `procedure.source` in the note of origin. (4) *The block.* The `procedures` block of the entry file lists the project's procedures after the framework's, links relative to the entry file. (5) *This repository.* `paths.procedures` is `docs/procedures`, in the adapter layer, with its first procedure `change-framework` (invocation `auto`: a core rule, a check, a role of the profile); its skill and row in `AGENTS.md` are generated.
- **Decisions / deviations from the plan:** a collision is an error of the generators, so `harness check generated` and `sync` report it (a check that throws is reported as its problem); no separate check. The folder is classified by the project's own layer map, so the tools say nothing about it. `profile/roles.md` is not changed: a template that a sync renders with the tools of an older version must use only roles those tools know, and the role is optional.
