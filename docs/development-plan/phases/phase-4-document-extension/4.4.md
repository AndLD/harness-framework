# 4.4 — Procedure `update-framework`

**Status:** ⬜ · **Agent:** C1 · **Size:** 3 SP

**Procedure `update-framework`**: Take a new version, from the version the lock names to the target, across any number of versions: `sync --from --to`, then `harness migrate` when the old `sync` did not start it (3.5); follow the migration notes of every version between, in order (3.11), doing each required action and its check; then verify (`check all` and the project's gate; the check of every required action; the probes that 3.15 selects, compared with the project's last review), and record what the notes missed; on a failure, `harness rollback` (3.14); the pull request. A consumer's own plan gets no migration task written for it, adopt a project that copied the first harness (`harness adopt`), and report or fix a defect found in a consuming project (an issue or a pull request in this repository, a tag, a sync there). Explicit invocation. Verified by following it on a scratch project pinned to `0.1.0` and taking the next development version in one jump; the commands it names are the roles of the profile.
