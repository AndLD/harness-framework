# 6.2 — Quiet by default: the output of the framework's commands and hooks

**Status:** ✅ · **Agent:** C2 · **Size:** 3 SP

**The biggest sink was output that nobody needed.** The framework's own commands (`harness check all` and each check, `flow dispatch`, `flow status`, `flow gate`, `plan summary`, `branch update`), the Git hooks (pre-commit, pre-push) and the runtime's hooks print **failures and a one-line summary** by default; the full text is behind `--verbose`, and a hook that runs a long suite writes its full output to a file and prints the path and the failing lines only, capped at a number of lines (a setting of the profile, with a default). A command that fails prints enough to act on it: the failing check, the file, the line. Exit codes and what a check holds do not change; a check's pass is one line, not one line per file.

- `harness flow dispatch` keeps the means for the executor (the app's call and the command line) and drops what a worker does not need; a `--brief` form prints the next step's command and its worker only.
- The audit of 6.1 shows the effect: the same commit, push and check sequence is measured before and after.

**For consumers too:** the commands and hooks are the framework's, so a project gets them by `harness sync`, and `harness init` writes the hook entries; the migration note says that the output changed (scripts that parsed it must use `--verbose`), and a consumer fixture proves that the hooks of a synced project are quiet.

**Verified by:** tests of each command's quiet and verbose output (a pass is one line; a planted failure prints its file and line), of the output cap and the full-output file of a hook, and of unchanged exit codes; the measured fall in the audit of 6.1 on a commit and push; `harness check all` passes; the migration note exists.
