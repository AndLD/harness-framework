# 6.5 — A restart threshold for the orchestrator, and steps paced for the cache

**Status:** ⬜ · **Agent:** C2 · **Size:** 3 SP · **Needs:** 2.7, 6.1

**A long session costs more than its size.** The workers have `reuseLimits.context` (40% of their window) and the orchestrator only has "restart when your context grows". This task gives the orchestrator a number: a flow setting for its own context limit (a default of about 50%, a setting beside `reuseLimits`), read through the runtime adapter's `context` role. At the limit it writes a **handoff entry** to the flow's log (the state, the decisions of the session, the exact next step, what it was waiting for) and continues in a new orchestrator session, started by the executor order of task 2.7 (the app's session first, the command line as a logged fallback, the owner by `manual`), which reads the flow file, the tail of the log and the current report, nothing older.

- **Cache pacing:** the dispatch tells whether the next step can start inside the cache window of the previous worker, so that a warm reuse is chosen on purpose and a wait that outlives the cache is logged as a cold start. The harness already measures cold and warm starts (`flow sample --start`); this task uses what the audit (6.1) and the samples show.
- `harness flow status` and `flow dispatch` print the orchestrator's context when the role can read it.

**For consumers too:** the setting is in the flow template, so new flows have it, and a consumer's existing flows get it by the migration note; the procedure `run-flow` and the runtime contract change, which needs the owner's approval in the pull request.

**Verified by:** tests of the threshold (below, at and above it, a runtime that cannot read the context), of the handoff entry's shape in `harness flow check`, and of the cache-pacing hint; a dry run of a restart on a fixture flow; `harness check all` and the conformance suite pass; the audit of 6.1 on a long orchestration before and after.
