# 3.17 — The Git guard checks the project's branch, not the branch of the repository a command acts on

**Status:** ✅ · **Agent:** C2 · **Size:** 2 SP · **Log:** [3.17.log.md](./3.17.log.md)

**The Git guard checks the project's branch, not the branch of the repository a command acts on**: `refusal(command, branch)` gets the branch checked out in the project directory, and treats `-C` only as an option to skip, so a command that changes directory first (`cd <other clone> && git commit`) or names one (`git -C <path> commit`) is judged by the wrong branch. Both ways are wrong: a commit to another clone's feature branch is refused while the project is on its integration branch (found on 2026-11-03 by a session of AndLD/bot-rts that edited this repository's clone), and a commit or push to another clone's integration branch is allowed while the project is on a feature branch, which is the unsafe case. Resolve the repository of each Git command in the line (a `cd` before it, `-C`, `--git-dir`, `--work-tree`) and judge it by that repository's branch and protected branches; a repository it cannot resolve is judged by the strictest rule. Verified by guard tests for each form, both ways.
