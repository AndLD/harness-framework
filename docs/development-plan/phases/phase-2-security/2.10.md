# 2.10 — Security rules of core, distilled from the first review

**Status:** 🟡 · **Agent:** C3 · **Size:** 3 SP · **Needs:** 2.4

**Turn what the first review found into a short set of security rules of core**, so that a project that is bootstrapped by the framework starts safer, and each review leaves the projects safer than the last. The task reads the report of 2.4, the findings that consumers have reported upstream so far, and the probes that failed, and for each decides: a rule of core, a probe or scenario to add or change, or nothing.

- **A rule** is one line with a rule id, written as the existing rules of the entry file are, and tied in the rule-to-check map to a check of `harness check security` (2.2) or to the probe it rests on. A rule is proposed only for something that happened or that a probe found; a rule from fear alone is left in the catalogue.
- **Each rule goes through the procedure `change-framework`**: it is a change of core and needs the owner's approval in its pull request. The task proposes, the owner decides.
- **Size of the always-loaded set**: the rules go in the entry file's rules or in the reading map, with the detail in the catalogue that agents read on demand. The task sets a line budget for the new rules and checks it with `harness review measure` (2.3).
- **Bootstrap**: the rules reach a new project through the same template as the other rules, so `harness init` gives a project the rules it has by the framework's version.
- **The trend**: the review log of the bindings records the number and severity of findings of each review, so the effect of the rules can be seen over the reviews.

**Verified by:** every new rule has its row in the rule-to-check map, and the check or probe it names exists; the budget of the always-loaded set holds; `harness check all` passes; the owner's approval of each rule is recorded in the pull request.
