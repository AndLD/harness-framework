# 2.2 — Automated security checks

**Status:** ⬜ · **Agent:** C2 · **Size:** 3 SP

**Automated security checks**: `harness check security`: a secret scan of the tracked files and of the history range of a push, with its patterns in the profile and no download; the dependency audit as a new optional stack role (`npm audit`, `pip-audit`); the host's CI checks (workflow `permissions:` declared, third-party actions pinned to a commit, no `pull_request_target` that checks out the head); and the runtime's settings checks (the `access.denyRead` rules present, no broad allow rule for shell or edits). Each check has tests with a planted defect.

**What "broad" means for the settings check** (added on 2026-11-05, at the owner's request, after the repository's own `.claude/settings.json` gained `Edit(docs/development-plan/**)`, and task 2.6 will write rules of that kind into the settings of any project): a rule that allows edits or shell commands for a whole project or for any command (`Edit(**)`, `Edit(*)`, `Bash(*)`, `Bash(rm *)`-style patterns on destructive commands) is broad and is reported. A rule limited to a named folder of the project (`Edit(<folder>/**)`) is not, as long as the folder is not the settings, the hooks or the Git directory; the project's profile may name the folders it allows. The test with a planted defect includes the rule of this repository as a case that must pass, and `Edit(**)` as one that must fail. How the check treats a command prefix such as `Bash(git *)` or `Bash(node *)` (the flow's workers use them, and the shell guard hook is what limits them) is not decided here: the task decides it with the owner and states it in the check's tests.
