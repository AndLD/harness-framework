# 2.7 — A flow starts its workers as nested sessions, and logs why when it uses the command line

**Status:** ⬜ · **Agent:** C3 · **Size:** 5 SP

Promoted from the backlog item [B-3](../../backlog/archived/B-3.md), whose source is owner.

The owner asked (2026-11-05) that the next runs of flows start each step's worker as a session nested under the orchestrator's session, as the first steps of flow 1 did, so the owner can open and follow it in the desktop app, and that this cause no more permission prompts than the flow's mode (brainstorm or seamless) requires.

**What happened in flow 1** (from its log and the orchestrator's transcript): steps 1, 1 (second run), 1a and 1b ran as nested sessions. At step 1c the app refused the orchestrator to start a session on the turn that a worker's report began, and the owner started it from a card. At step 1d the worker had to run in the consumer's folder, which a proposal card cannot carry, and after the owner remarked that running `claude -p` was their rule in the repository, the orchestrator started 1d and 1e, and after the re-run of 1e as a session, steps 1f to 3, on the command line, each in a worktree under the flow's `permissions`. No file of the repository says that `claude -p` is a rule: the executor default of the procedure is `session`, and the log named the command line "the owner's usual way" only. A `claude -p` worker is not shown in the desktop app, and the flow's `permissions` setting applies to it alone.

**What was found by experiment** (2026-11-05, three read-only haiku sessions, one observation each, so read it as an indication and repeat it in the task):

- In this project, the app allowed a worker session to start from the follow-up turn that the end of another worker began, three times in a chain (the first from the owner's message).
- A start with another repository's folder (`cwd`, the consumer `bot-rts`) was denied by the app's auto mode classifier, without a reason, on the follow-up turn after a worker ended; the same start was allowed on the turn that the owner's own message began. The proposal card cannot carry a folder either. So an orchestrator cannot start a consumer step by itself after a worker's end, and the owner's message would be needed for each one.
- The orchestrator's session was in auto mode, and a started session inherits its permission mode or a lower one; the experiment's workers only read a file, so the prompts of a worker that runs `git`, `gh`, `npm` and `node` were not tested.

**What is wanted** (the proposal, not the design): the order of the executors, discussed with the owner on 2026-11-05 and not decided as a whole (the owner decided only the case of another repository, below): a session of the desktop app is the default of every step in the home repository; a worker on the command line (`claude -p`) is the fallback of that, for one step at a time, logged as a decision with its reason and never carried to the next step by habit; the owner pasting the prompt (`manual`) is the fallback of the fallback; and a subagent stays outside the order, for a short step of analysis only. Today the command line is listed under the `session` executor, so a switch to it leaves no trace in the log: it becomes its own named executor in the log and in the dispatch. For a step in another repository the owner decided (2026-11-05) that the worker runs on the command line, logged as the fallback with the reason above, so that a flow in seamless mode does not wait for a message; the dispatch says so for such a step. The permission mode a worker starts in (the app's `permission_mode`) is decided by the flow's settings and logged, and what the flow's `permissions` allow is also given to a nested session by the means the runtime has (its mode and the project's allow rules), so a worker asks no more than a `claude -p` worker under the same settings. The owner's choices of 2026-11-05 are in B-2 and its task 2.6, which already let the plan's files be written without a prompt.

**Before it is built:** the order of the executors (a session of the app, then the command line, then `manual`, a subagent outside it) was discussed and not decided as a whole; the owner confirms it in the pull request of this task, since it changes the meaning of the procedure `run-flow` and of the runtime contract, which needs the owner's approval. The case of another repository (the command line, logged as the fallback) is decided.

**Verified by:** tests of the dispatch (the executor named in the log is the one that was used, so a switch to the command line shows; a step in another repository is dispatched on the command line with the reason; the permission mode of a nested session is printed from the flow's settings); the conformance suite of the runtime adapter with the changed contract; `harness flow check` on a log that names the fallback; and the experiments repeated once with a worker that runs `git`, `gh`, `npm` and `node`, to see what it asks in the mode the flow sets.
