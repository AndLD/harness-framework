# 2.6 — A switch that lets an agent write the plan's files without a prompt

**Status:** ⬜ · **Agent:** C2 · **Size:** 3 SP

Promoted from the backlog item [B-2](../../backlog/archived/B-2.md), whose source is owner.

The owner asked for a command, with an on and an off word, that lets an agent write the files of the plan (logs, flow files, plan documents) without a permission prompt in the agent runtime, and for the same setting during bootstrap of a project, on by default.
The reason: a session that appends to a log or edits a table cell stopped for the owner's approval many times in one flow, also in a flow's seamless mode, which decides flow questions and not the runtime's tool permissions.

**What was found when the request was discussed** (2026-11-05, a headless `claude -p` with the setting sources limited to a scratch project, one rule set per run; one observation each, so read it as an indication and repeat it in the task):

- A rule that allows the command (`Bash(cat >> *)`) does not stop the prompt for a heredoc append: the `>>` is checked as a write to a file, so the command ran only when the write was allowed too.
- The write is allowed by the runtime's accept-edits mode, or by an edit rule (`Edit(**)`), without any rule for the command itself. A folder-limited edit rule (`Edit(docs/**)`) let the append run inside the folder and refused it outside; a write outside the project folder always prompts; `sed -i` still prompted in both cases.
- The same write permission governs the runtime's own edit and write tools, so a session in the default mode prompts for them as well: choosing between a heredoc and an edit tool does not change the prompts; the write permission does.
- One compound line (`git status && cat >> … <<'EOF'`) was refused by the runtime's parser ("Parser did not consume trailing input"), not by a permission; the cause was not found.

**What is wanted** (the proposal, not the design): one command of the runtime adapter that turns the write permission for the plan's folders on and off by a word, reports its state, and writes the project's shared, tracked `.claude/settings.json` (the owner's decision, 2026-11-05: a tracked file reaches every checkout and every worktree of a worker, which an ignored local file does not); the project's local file or the user-wide one only when the owner asks for it by name. The bootstrap of a project turns it on without asking (the owner's decision, 2026-11-05: it writes the project's own `.claude/settings.json`, so it shows in the project's diff, and reaches only the plan's folders), says in its output what it set and how to turn it off, and takes an option to leave it off; the user-wide setting is never turned on by the bootstrap. The repository's own `.claude/settings.json` already has the rule for `docs/development-plan/**` (pull request 132), so this task builds the command and the bootstrap, and must keep that file valid under `harness check scaffold`. The folders are a setting (by default the plan, the flows and the logs, never the settings file itself, the hooks or the Git directory). It is a role of the runtime adapter, so core names no runtime and another runtime may fill it; adding the role is a change of an adapter contract and needs the owner's approval in its pull request.

**Verified by:** unit tests of the command (on, off, state, the folders setting, a settings file that has other rules or none, a user-wide file untouched) with the file system root as a parameter; the conformance suite of the runtime adapter with the new role; a bootstrap test that the rule is written to a project's `.claude/settings.json` and that the option to leave it off writes nothing; and the observations above repeated once in a scratch project with the written rule (the folder is allowed, a path outside it and `sed -i` still prompt).
