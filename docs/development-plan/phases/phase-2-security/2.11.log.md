### 2026-11-06 — a session starts in the mode of the flow's permissions; the experiment repeated with a worker that runs Git, `gh`, npm and Node
- **Branch:** `feature/2.11-nested-worker-permissions` — done, built by the worker of step 1a of flow 2, itself a nested session of the desktop app (`CLAUDE_CODE_CHILD_SESSION=1`, unattended), started by the owner from a card at 2026-11-05 22:59Z after the app refused the orchestrator's own start on a turn that a worker's end began (the case of task 2.7, met again).
- **What was built:** (1) The Claude Code preset's `session` executor passes the mode of the flow's `permissions` setting to the app's `start_session` as `permission_mode`; its `reads` says that the app refuses a mode above the orchestrator's own, so the start then fails and the fallback runs the step. (2) Its `permissions` line names the mode, and names the tools of `allow` as allow rules for the project's settings (`.claude/settings.json`, or the local `.claude/settings.local.json`), because the app's start takes no tools; the owner adds the missing ones (the procedure `run-flow` says to tell the owner). (3) `harness flow dispatch` logs the mode in the "step started" line (`· **Permissions:** <mode>` after the model, only when the flow sets a mode), for the step and for its fallback. (4) The runtime contract (a minor addition to contract 2), the plan method (section 10), the procedure `run-flow`, the flow-log template and a changelog fragment. Tests: the adapter's session start and line, and a dispatch through the real preset that prints the mode, the allow rules and the logged mode.
- **What the app's start takes** (read from the app's bundle, version 4.16336.0): `start_session` has `permission_mode` ("the permission mode it starts in, this session's own or a lower one (omit to inherit it). A higher mode, or one the app does not offer here, is refused"); the order of the modes is plan < default = dontAsk < acceptEdits < auto < bypassPermissions. It has no input for tools. `set_session_permission_mode` raises a session's mode only through a card the owner approves. A new worktree of the app gives priority to `.claude/settings.local.json` and `.claude/settings.json` among the files it carries over; whether an ignored local file is always carried was not tested.
- **The experiment, repeated once** (this session, mode `acceptEdits`, the orchestrator in `auto`; one observation, read it as an indication): allowed without a prompt: `git` (fetch, status, log, commit, push, checkout), `gh` (pr create, pr list, pr view), `npm` (test, run lint, run docs:check), `node` (scripts and `-e`), `sed`, `ls`, `mkdir`/`rmdir` in the worktree, and `grep`, `head` and `tail` inside compound lines. Refused ("requires approval", which an unattended session cannot answer): `python3`, `printenv`, `npx`, `claude`, a heredoc with an unquoted delimiter and `${…}`, a compound `cd … &&` line with an output redirection, and any read or listing outside the worktree by a shell command (`grep`, `ls`) — reads by `node` outside it were allowed. So the session asked for exactly what lies outside the flow's `allow` list (`git`, `gh`, `npm`, `node`, `sed`, `ls`) plus the read-only commands, which matches what a `claude -p` worker of step 1 was refused (`python3`, heredocs with `${…}`); a compound line with `grep` or `tail` was allowed here, where step 1 found it refused.
- **Problems / blockers / findings:** (1) No settings file names the tools this session was allowed (the project's and the user's settings hold no allow rule for the shell, and no managed settings exist); the likeliest source is the app, which copies a parent session's session rules to a session it starts (`sessionPermissionUpdates`, "toAnotherSession", in the bundle), but this was not verified. So whether a session started by the orchestrator, not from the owner's card, gets the same tools is open; the line of the dispatch tells the owner to add them to the project's settings, which holds either way. (2) **Whether a `claude -p` worker is woken after its turn ends** could not be tested from here: this session is refused `claude`. The question stays open, and the preset keeps `wakeups: false` for `cli`. How a `cli` worker waits for a pull request, by the means it surely has: it does not end its turn while it waits; it enables auto-merge and polls the checks within the turn (`gh pr checks <n> --watch`, which returns when they end), then confirms the merge (`gh pr view <n> --json state`). (3) The push was refused by the pre-push hook of the main checkout (issue I-19, met a second time); pushed with `git -c core.hooksPath=<the worktree>/tools/git-hooks push`.
- **Decisions / deviations from the plan:** the change gives the flow's mode to a session, where the contract said a session runs under the application's settings; it is written as a minor addition (an adapter whose application takes no mode still conforms), under the task's own "What is wanted" and the owner's confirmation of task 2.7 (the entry "2026-11-05 22:40 — decision D3" of the log of flow 2). The allow rules are named for the owner to add, not written by the orchestrator: the settings file is the owner's, and an agent that grants itself tools is what the permission system guards against.
