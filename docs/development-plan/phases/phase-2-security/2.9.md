# 2.9 — Security probe catalogue and attack scenarios for the product (S5 and S6)

**Status:** 🟡 · **Agent:** C3 · **Size:** 5 SP · **Needs:** 2.1

**The first edition of the catalogue for what a project builds and runs**: `core/reviews/security/probes/`, the files of S5 (the product's attack surface) and S6 (operations), and `core/reviews/security/scenarios/`, the playbooks of attack scenarios that a consumer's agent or team can run against its **own** test environment, like a penetration test, under the rules of engagement of 2.1. The owner is not a security expert and relies on the depth of this task, so it is a research task, like 2.8.

**Direction** (what to search for, not a fixed list):

- A threat-model procedure for the bindings: assets, trust boundaries, entry points, who the attackers are; written so that an agent can produce it from the project's code and documents and a person can check it.
- The OWASP Top 10 categories, one probe set each, and the OWASP Application Security Verification Standard and Web Security Testing Guide as the source of what to verify and how, read in their current edition and named with its date.
- Authentication flows: registration, login, password reset, sessions and tokens, multi-factor, single sign-on; for each, the gaps to look for (enumeration, weak reset, session fixation, token leakage, missing rate limits).
- Authorization: the permission matrix of the product, tested object by object and role by role (access to another user's data, privilege escalation, missing checks on the server side).
- Input and output: injection of every kind the stack has, cross-site scripting, request forgery, server-side request forgery, unsafe file upload and deserialization, path traversal, unsafe redirects.
- Isolation of untrusted code and content, abuse limits, secrets in the client, exposure of the API and its documentation, error and debug output, logging and monitoring of attacks.
- S6: deployment configuration, backups and their restore, incident response, the retention of logs.
- Scenarios: each playbook has a goal, preconditions, steps that run against the project's test environment, the safe behaviour that is expected, the evidence to keep, and the cleanup. Several different attack scenarios per area, so a review does not rest on one path.

**Rules for the work:** the scenarios are for the project's own system in a development or test environment, as the rules of engagement say, and never name a target outside it; core stays neutral (a stack's tools go through adapter roles); sources are summarized and referenced, never copied; each probe marks how far a script can decide it.

**Verified by:** every probe and scenario has an id, its sources with their dates, and the evidence it asks for; `harness check all` and the CORE scan pass; a pass by a fresh worker that did not write the catalogue (another model when one is available) reads each probe against its cited source and each scenario against the rules of engagement, and logs what it disputes; the catalogue says it is a first edition and a draft until a person with security expertise has reviewed it.
