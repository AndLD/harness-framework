# 2.1 — Security review method: the frame, the probe format and the rules of engagement

**Status:** ✅ · **Agent:** C3 · **Size:** 5 SP

**Security review method, the frame**: `core/reviews/security/README.md` (dimensions S1 to S6 of section 11.1, scoring from 1 to 5 with evidence, procedure, findings with severity, cadence) and `_template.md`, a bindings template, the procedure `security-review` packaged per runtime, and a row for it in `core/reviews/README.md`. The code review's security dimension (C7) links to it instead of repeating it. The method is written for the consumer's agent or team to review its **own** project, and it states its direction instead of fixing a list: the catalogue of probes that tasks 2.8 and 2.9 research grows with every review. The task defines:

- **The probe**, the unit of the catalogue: an id, its dimension, what it checks and why, how its evidence is gathered (a command through an adapter role, a file to read, an agent's judgment, or a test scenario), severity guidance, when it applies (every project, a stack, a kind of product), how far a script can decide it (scriptable, judged, manual), and its sources with the date they were last verified. The method says how a project adds probes of its own in its bindings.
- **The rules of engagement** for any active test or attack scenario: only the project's own system, in a development or test environment, never production and never a third party's system; nothing destructive; the scope written in the bindings before a scenario runs; test data only; an agent that would leave the scope stops and asks.
- **Where the results go**: dated reports stay in the project; each finding becomes an issue of its queue, with its severity; a finding that is generic is reported upstream (the procedure `report-upstream`). The bindings say where reports and the review log live.
- **The loop**: a review ends by sorting each finding into a fix, a probe to add or change, or a candidate for a security rule of core (task 2.10 distils them).

**Verified by:** the CORE scan returns 0 on the new files; `harness check all` passes; the procedure is in the package of each runtime the framework ships; a pass by a fresh worker that did not write the method (another model when one is available) reads it against section 11.1 and logs what it could not follow. The method is exercised on a real repository by task 2.4.
