# 2.8 — Security probe catalogue for the project and its supply chain (S1 to S4)

**Status:** ✅ · **Agent:** C3 · **Size:** 5 SP · **Needs:** 2.1

**The first edition of the catalogue of probes for the dimensions every project has**: `core/reviews/security/probes/`, one file per dimension: S1 secrets, S2 dependencies and supply chain, S3 CI and the repository host, S4 the agent harness. A probe has the format that 2.1 defines. The owner is not a security expert and relies on the depth of this task, so it is a research task: the worker finds what the established sources ask a review to look at, and does not stop at the list that section 11.1 of the design gives.

**Direction** (what to search for, not a fixed list):

- The sources: the OWASP cheat sheets for secrets management and for CI/CD security, the OWASP Top 10 for large-language-model applications and the OWASP work on agentic security (S4), SLSA and the OpenSSF Scorecard checks (S2, S3), the NIST secure software development framework, and the documentation of the repository host's own security features. Each is read in its current edition and named with its date; a source that cannot be read is said so, never replaced from memory.
- S1: secrets in tracked files and in history, in environment files, in logs, in the transcripts of agents, in build output and images; the read exclusions for agents; rotation after a leak.
- S2: lock files and audits, pinned and verified dependencies, install-time scripts, tools that download at run time, the vendored framework's hashes, the provenance of release artifacts.
- S3: workflow permissions and triggers, secrets that reach a pull request from a fork, third-party actions, branch protection and required checks, who may merge and release, the tokens of the host.
- S4: runtime permissions and allow rules, hooks that run code on tool input, untrusted text that agents read (issues, pages, comments, tool output) against the instruction boundary, connected tool servers, push and merge authority, what an agent can send out.
- For each dimension: what an attacker or an accident does, so a probe states a scenario and not only a rule.

**Rules for the work:** core stays neutral, so a probe that needs a stack's command names an adapter role and does not name the stack; text of a source is summarized and referenced by its id, never copied (the licences differ); a probe marks how far a script can decide it, so that task 2.2 starts from the scriptable ones.

**Verified by:** every probe has an id, its sources with the date, and the evidence it asks for; `harness check all` and the CORE scan pass; a pass by a fresh worker that did not write the catalogue (another model when one is available) reads each probe against its cited source and logs the probes it disputes, which are fixed or marked disputed; the catalogue says it is a first edition and a draft until a person with security expertise has reviewed it, and the review log of the bindings records who did.
