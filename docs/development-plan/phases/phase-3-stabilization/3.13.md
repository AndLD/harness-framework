# 3.13 — The issues found in use are kept as a phase, though they are not one

**Status:** ✅ · **Agent:** C2 · **Size:** 7 SP · **Needs:** 3.10, 3.12 · **Log:** [3.13.log.md](./3.13.log.md)

**The issues found in use are kept as a phase, though they are not one**: the open-ended phase has no goal, no exit criteria and no end, its size "grows" and distorts the totals, and it takes a number in the sequence of phases (Phase 3 here; Phase 12 in the consuming project). Its rows also mix defects with design work that belongs to a phase. Make it an **issue queue** next to the phases (the owner's decision of 2026-11-03): (1) `development-plan/issues/`, in the layout of 3.10 (a file per issue, its log beside it), with ids of its own (`I-<n>`) and branches `bugfix/I-<n>-<slug>`; the plan index shows the open issues and their size apart from the phases' totals. Each issue records `Reported:`, every report on the host that points to it (several reports can be one problem), and an area from the list of 3.11; the queue's index and its archive show the title and the area, so that a new report is matched against the indexes before any issue file is opened (3.16). (2) **Finished issues are archived**, so that the queue holds only work to do: the queue's index `issues/README.md` lists the open and in-progress issues only; when an issue is done, the plan-summary command moves its file and its log to `issues/archived/`, lists it in the generated archive index `issues/archived/README.md`, and rewrites the links to it as 3.10 does. An agent that works the queue reads the open index, never the archive. (3) The plan method, the templates and the scaffold, the profile roles (`openEndedPhase`, `openEndedPhaseNumber` give way to the queue's path), the Git rules, the entry file's role binding and the resume phrases ("Work the issue queue", "Fix I-<n>", approving their pull requests as "Start Phase N" does). (4) **A move never renames a planned task**, so that orders written by id survive: a migration script (3.12) turns a consumer's open-ended phase into a normal phase that keeps its number and every id, with a goal and exit criteria made of its remaining tasks; only its defects that have not started become issues, each naming its old id (`I-1, formerly 12.5`); a task in progress never moves. Issues found after that go to the queue. (5) `check plan` fails when an order of development or an execution-order line names a task id that exists nowhere (in a phase, or in the queue or its archive under its old id). (6) Last, this plan: Phase 3 becomes a normal phase ("Stabilization, migrations and local adapters"), its open defects (if any) become issues, and it ends with 3.4. Needs 3.10 and 3.12 first. Verified by tests of the tools on a queue (an issue done and archived, the links rewritten), by the migration test from the earlier tags, by a fixture whose order names a moved task, and by `check all` on the framework after its own move.
