# 3.21 — A backlog item can be started as it is, though it is a request nobody has approved or placed in a phase

**Status:** ✅ · **Agent:** C2 · **Size:** 5 SP · **Needs:** 3.20 · **Log:** [3.21.log.md](./3.21.log.md)

**A backlog item can be started as it is, though it is a request nobody has approved or placed in a phase**: 3.20 gave the backlog its own statuses (⬜, 🟡, ✅), its own branch (`feature/B-<n>-<slug>`) and an archive of done items, so B-1 was built, finished and archived inside the backlog, and an order of development may name `B-<n>` as work. The owner's intent is the opposite: the backlog is the place for what is **not approved yet**, with no phase and no release (a to-do before the to-do). An item is **never started as it is**; it is **promoted** first, by the owner's decision, into a task of a phase of the plan, and only that task is claimed, branched, built and logged.

Delivered:

1. **The status of an item.** An item is `Proposed` (the only open status; there is no 🟡 and no ✅, so nothing can be "in progress" in the backlog) or `Promoted`, with `Promoted to:` naming the task it became. `Agent` and `Size` become optional on a proposed item (an estimate belongs to the task), and the template, the checks and the index say so.
2. **Promotion.** `harness plan promote <B-n> --phase <n>` (the owner's decision is the reason to run it; the command refuses without `--approved`, as the commands that change the host do) creates the task in the phase: the next free id of the phase, from the task template, with the item's title and description and a line that names the item (`Promoted from B-<n>`), `Status` ⬜, and the `Agent` and `Size` the owner gives or the item holds; it sets the item to `Promoted` with `Promoted to: <task id>`, moves the item to `archived/`, follows every link, and runs the plan summary. The item's `Source:` is copied to the task, so a report that asked for it still finds it.
3. **Not startable.** An order of development, an execution order or a `Needs` that names a `B-<n>` is a problem of `check plan` ("a backlog item is not approved work: promote it first"); a name that an item took over (`Formerly`) still resolves. The branch type `feature/B-<n>-<slug>`, `Plan: B-<n>` and the claim of an item disappear from the plan method, the template and the session-start line (which says how many items wait for the owner's decision). "Work the issue queue" and the other phrases already approve no item; the plan method says that the way in is promotion.
4. **Triage.** A feature request still becomes a `Proposed` item with `Source: report` and the link, the answer to the report says that it waits for the owner's decision, and `reports plan` says so.
5. **What was built before this task.** B-1 (the probe switch, built and archived as an item by 3.20 and B-1's own pull request) is promoted retroactively by the new command into a task of this phase, 3.22 (done, with B-1's log beside it), so that the plan shows it where a task belongs.
6. **The migration note.** `migrations/0.2.0-dev.3.md` is updated (it is not frozen until the version is cut): a project that started a backlog with the first statuses sees its items read as `Proposed` or `Promoted`, and the note says what to change by hand.

Verified by: tests of the status line of an item (both statuses, a missing `Promoted to:`, a ⬜ on an item), of the promotion (the task file, the item's move, the links, the source copy, a refusal without `--approved`, a phase that does not exist) and of the checks on an order that names an item; `npm run docs:check` and the tests on this repository, where B-1 reads as the log of this task records.
