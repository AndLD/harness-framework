### 2026-11-04 — the issue queue, its archive, and the move of the open-ended phase
- **Branch:** `feature/3.13-issue-queue` — done. It needs 3.10 and 3.12; it branched from 3.10's branch while that pull request was open.
- **What was built:** (1) *The queue.* `paths.issues` (a profile role with a default; the folder of the queue) holds `README.md` (the generated index of the open and in-progress issues), `I-<n>.md` (a status line with `Status`, `Agent`, `Size`, `Area`, `Reported`, optional `Formerly` and `Log`, then the description), `I-<n>.log.md`, and `archived/` with its own generated `README.md`. Branches are `bugfix/I-<n>-<slug>`, claims and commits carry `Plan: I-<n>`. `tools/lib/issue-queue.mjs` reads and checks it; the area is one of the names of `migrations/areas.json` or `Unclassified`. (2) *Archive.* `harness plan summary` moves a done issue and its log into `archived/`, lists it in the archive's index, and follows every link to them (`tools/lib/link-moves.mjs`, the code the phase split shares); the plan index gets a line of its own for the open issues and their size, apart from the totals. (3) *Rules and templates.* The Git rules (Role binding line, §7.1, the plan-work approval: "Work the issue queue", "Fix I-<n>"), the profile roles, the plan method (new section 8, an issue template), `start-task`, the scaffold (a new project gets the queue and its archive, no open-ended phase) and the session-start hook (a line with the number of open issues). `plan.openEndedPhase` and `plan.openEndedPhaseNumber` stay in the schema as deprecated, so that an older profile file loads. (4) *The migration* is part of the script `migrations/0.2.0.mjs` (`tools/lib/issue-migration.mjs`): the open-ended phase becomes a normal phase that keeps its number and every id (title size, goal and exit criteria made of what remains), its tasks that have not started and that no order of development names become issues (`Formerly: 12.5`, area `Unclassified`), a task in progress or done never moves, and the profile file loses the two keys and gains `paths.issues` (a text edit that keeps its formatting). (5) *`check plan`* fails when an order of development or an execution order names an id that exists nowhere: in a phase, in the queue, or in the queue under its old id. (6) *This plan:* Phase 3 is a normal phase, "Stabilization, migrations and local adapters" (folder `phase-3-stabilization`, 56 SP, ends with 3.4); its only defect that had not started, 3.19, is issue I-1 (`Formerly: 3.19`, area "bootstrap and sync", reported by issue 30).
- **Decisions / deviations from the plan:** a task that has not started stays a task when an order of development names it (the planned work of this repository's Phase 3 is not a defect), which is how the generic script tells defects from planned work. The migration cannot classify an issue's area, so it writes `Unclassified`, which the check accepts. The renamed folder of Phase 3 changed no task id.
