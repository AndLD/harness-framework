### 2026-11-04 — scripts, the record in the lock, and the migration test
- **Branch:** `feature/3.12-migration-scripts` — done. It needs 3.5, so it branched from that task's branch while its pull request was open.
- **What was built:** `harness migrate` (`tools/lib/migrate.mjs`) runs `migrations/<version>.mjs` of the vendored tree for every version after the project's own up to the target that `migrations.applied` of the lock does not hold, in version order, recording each as it finishes (a stopped run resumes); then regenerates the managed files; then prints the notes of those versions in order. The lock gets `migrations: { version, applied }`; a bootstrap writes `{ version, applied: [] }`; a lock without it counts as `0.1.0`. A script is `export default ({ root, profile }) => lines`, checks its starting state and can run twice. A development version (`0.2.0-dev.n`) runs the script of `0.2.0` without recording it as applied, so each next development version and the final one run it again. `tools/lib/versions.mjs` compares versions. In mode `self` and in a detached project `migrate` only regenerates. `migrations/README.md` documents the scripts. **The migration test** `tests/migration/released-tags.test.mjs`: for each tag `v*.*.*` of the history it exports the tag, bootstraps a project with that tag's own tools, takes the current tree (this repository, one minor version ahead so that the scripts of the version in preparation apply) with the project's own `sync`, then `migrate` (or `sync` again where the old sync stopped), and requires `check all` to pass.
- **Decisions / deviations from the plan:** the test runs on every released tag (`0.1.0`, `0.1.1`, `0.1.2`), not only `0.1.0` and `0.1.1`; it needs the tags (CI fetches the full history). The tools of `0.1.0` and `0.1.1` do nothing when started through a symbolic link (task 3.3), so the test uses real paths for its folders (a temporary folder on macOS is a link). No real migration script exists yet; the first ones come with 3.10 and 3.13 (`migrations/0.2.0.mjs`). The migration note of `0.2.0` (written by the release) must tell a project on `0.1.x` to run `migrate` after its `sync` (that `sync` cannot start it), and to `sync` again if its old `sync` stopped on a rule it could not render.
- **Verified by:** `tools/lib/migrate.test.mjs` (scripts in order with notes in order; a script run twice with no change; a stopped run resumed; a development version then its final version; self mode; the version comparison) and the migration test from all three tags; `npm test`, lint, typecheck, `npm run docs:check`. **Not verified:** the first real script (none yet); a consumer.
- **Problems / blockers / findings:** none.
