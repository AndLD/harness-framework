# 3.20 — A feature request from a user has no place in the plan but the issue queue, which is for defects

**Status:** ⬜ · **Agent:** C2 · **Size:** 5 SP

**A feature request from a user has no place in the plan but the issue queue, which is for defects**: the triage of reports (3.16) can turn a report into an issue only, so a request for something new (the probe switch of report 65 became I-6) sits among the defects, and "Work the issue queue" would approve building it. The owner asks for a **backlog queue** for feature requests, beside the issue queue and not instead of the plan: a request waits there until the owner puts it into a release or a phase.

Delivered:

1. **The queue.** A folder named by a new profile role (`paths.backlog`, absent in a project that has no backlog, as `paths.issues` was), with an index of the open items that `harness plan summary` generates (and the plan index shows, as it shows the issue queue), an `archived/` folder for done items, and a file per item `B-<n>.md` from a backlog template of `core/plan/` (ids permanent, never reused; the next free number counted over the index and the names in `archived/`). Its scaffold templates are written by `sync`, and `check plan`, `check links` and `check layers` hold the folder as they hold the issue queue.
2. **The source tag.** Every item has a `Source:` field that says where it came from: `GitHub issue` with the link of each report (an item can gather several), or `owner` / `agent` for an item that did not come from a report. The index shows the column.
3. **Triage.** `harness reports plan` gains the relation `feature` (a request for something new, not a defect): it says to add a backlog item with the report as its source, or to add the report to the source of the item that already holds it, and to answer the report with the item's id. The procedure `triage-reports` and the method name the relation, and `reports candidates` also compares the open items of the backlog.
4. **Out of the issue queue.** The queue's text says that a feature request goes to the backlog; "Work the issue queue" and "Fix I-<n>" do not approve a backlog item, and its branch is `feature/B-<n>-<slug>`. The owner promotes an item by naming it in the order of development of the plan index (or by adding a task for it), and the item records where it went.
5. **I-6 is the first item.** I-6 (the probe switch, [report 65](https://github.com/AndLD/harness-framework/issues/65)) moves to the backlog as `B-1` with `Formerly: I-6` and its source, and this task writes it in the plan index in place of the issue.
6. **A project takes it.** The script of the version that ships this (named for the final version, as `migrations/0.2.0.mjs`) adds nothing a project did not choose: the backlog is optional, and the note of the version says how to set it up (the profile role, then `sync --local`) with the check that proves it.

Verified by: a test of the reading of the queue, of the index and of the new relation (a pure function with the seam as a parameter, as the issue queue's); `check plan`, `check links` and `check layers` on a backlog with an item of each source and on a broken one; the conformance of the presets; and `npm run docs:check` and the tests on this repository, which holds its own backlog with `B-1`. The task records in its log the choices it makes that this text leaves open (the id prefix `B-`, the name of the profile role).
