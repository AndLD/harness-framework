# 3.4 — Adapters of a project's own repository (`local:`)

**Status:** ⬜ · **Agent:** C2 · **Size:** 5 SP · **Needs:** 3.5, 3.12, 3.14

**Adapters of a project's own repository (`local:`)**: design §5 step 1 says a project that cannot wait for a release keeps an adapter in `harness-adapters/<kind>/<name>/` and names it `local:<name>` in the profile file, but the tools load only the adapters of the framework tree. A team whose stack, host or agent runtime the framework does not cover (Go, GitLab, Copilot) cannot adopt it until a release adds the adapter. Build it (the owner's decision of 2026-11-03): (1) the tools load an adapter from `harness-adapters/` when the profile names it `local:`; (2) `sync`, `harness migrate` (3.5) and `check vendored` leave that folder alone, and rollback (3.14) restores it with the rest; (3) `harness adapter test` runs on a local path, and `check all` and `migrate` run it on every local adapter, so a release that changes the adapter contract fails the migration with a message that names the adapter and the contract change (the migration note says what changed); (4) the procedure `new-adapter` offers both ways (into the framework, or local) and says how a local adapter is sent upstream later. Needs 3.5, 3.12 and 3.14 first (the migrations it must pass). Verified by a fixture project with one local adapter that passes `check all`, migrates across a version that changes the contract, and rolls back.
