# 3.10 — A phase is one long file, and a finished task is logged twice

**Status:** ✅ · **Agent:** C2 · **Size:** 6 SP · **Log:** [3.10.log.md](./3.10.log.md) · **Needs:** 3.12

**A phase is one long file, and a finished task is logged twice**: an agent that resumes a phase reads the whole phase file, most of it the rows of tasks it does not need. In the project this framework was extracted from, a resuming probe read about 7,200 words (budget 6,000), and one phase file's task rows hold 2,266 words for 18 tasks. Also, when no task is in progress the session-start hook takes the "next step" only from the phase log, so agents write every finished task there as well as in the task's own log: 15 of 23 entries of one phase log restate a task log, and the framework's Phase 1 log does the same (5 of 7). The copies drift. (1) **Layout.** A phase is a folder `phases/phase-<n>-<slug>/`: `README.md`, the phase index (goal, order, exit criteria, and a task table generated from the task files: id, title, agent, size, status, link); `<id>.md` for each task (its description, status, size, `Agent` marker, dependencies and a link to its log); `<id>.log.md`, the task's append-only log, next to it and separate from it (a task's log is about seven times its description, and most readers need only the description); `log.md` for phase-wide matters only (decisions, pauses, the close of the phase). A finished task writes only its own log, and its "next step" names what follows. (2) **Tools.** The plan-summary command writes the phase index table as well as the plan index; `check plan` holds the layout (the title size from the task files, a status, size and marker in every open task file, every log link resolves); the session-start hook prints the newest "next step" across the phase log and the task logs, by entry date, and the open tasks of the phase (id and title); the same code is the migration script of `0.2.0` (3.12), which splits a consumer's open phases, and a command that splits a phase by choice (a finished one, for example); it moves the phase's task logs, and rewrites every link into the phase and its logs, anchors included, across the repository (in the consuming project, 24 files link to one of the phases it will split), so that a consuming project migrates in one step. The tools still read the one-file layout, so finished phases are not migrated. (3) **Method and templates.** Method §6, the plan method, `start-task` (read the phase index and the task file, not the other tasks), `end-session` and `finish-phase` say so. The phase template becomes a phase-index template and a task template; the task-log template stays. (4) The framework splits its own open phases (2, 3 and 4). Needs 3.12 first (its split is a migration script). Verified by tests of the plan summary, `check plan`, the hook and the split command on fixtures in both layouts (the split leaves no broken link), by the CORE scan and the generated skills, and by the consuming project's probe P2 within its budget after it migrates. Found by the closing review of the extraction (finding H-20261103-05 of AndLD/bot-rts).
