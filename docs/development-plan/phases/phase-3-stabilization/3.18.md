# 3.18 — Nothing merges a green pull request unless someone comes back, and a consumer is never set up for it

**Status:** ✅ · **Agent:** C2 · **Size:** 5 SP · **Needs:** 3.11 · **Log:** [3.18.log.md](./3.18.log.md)

**Nothing merges a green pull request unless someone comes back, and a consumer is never set up for it**: the Git rules say "do not poll CI" and also "when CI is green, merge and go on", but a session gets no signal that its checks passed, so plan work waits for the owner after every pull request; and "never enable auto-merge unless the user asks" keeps the host from merging. Found on 2026-11-03 in the consuming project and here. (1) **The rules:** an agent enables the host's auto-merge on exactly the pull requests it may merge without asking (the task and plan-related pull requests of named phases), as the last step once the task's definition of done holds; never on one into the production branch, a release or hotfix branch, or one that needs the owner's approval; and the Git guard refuses it there. Waiting: never by checks the model repeats; the runtime adapter names how a session waits (the desktop app of Claude Code: its monitor wakes the session on a failure, and auto-merge merges; the command line: one background wait per pull request). (2) **The gaps of auto-merge:** when the checks are already green the host merges at once ("clean status"), which is expected; after pushing a fix, the session checks that auto-merge is still on; a task that needs the previous one branches from its branch (one level, no deeper), and a script brings in the integration branch after the squash merge and resolves the conflicts that only that squash causes; the wrap-up lists the pull requests that wait for the owner. (3) **The GitHub adapter:** `harness host protect` sets the ruleset, turns on "allow auto-merge" and keeps "delete head branches" off (the branch-retention rule); with `host.protection`, the adapter's scaffold adds a workflow that, when the integration branch moves, updates every open pull request with auto-merge on, so that a required up-to-date branch does not stall it. (4) **Every consumer by default:** bootstrap asks the host what it offers and runs the host setup: a repository that can be protected gets the ruleset, auto-merge and the workflow (`host.protection: true`); one that cannot (a private repository on a free plan) gets `host.protection: false` and one line on what going public or a paid plan adds; a person without admin rights gets the files and the one command for the owner. Interactive bootstrap says what it will set and asks once; `--no-host-setup` skips the step. (5) **A consumer can turn it off:** a profile switch `autoMerge`, on by default where `host.protection` is `true` and off where it is `false` (nothing would require the checks there); off brings back the old behaviour, where the agent asks before merging. The core rule, the guard and bootstrap read it. (6) The migration note of the version tells an existing consumer to run `harness host protect` again, with its check (a setting of the host is not a file, so no script can do it), and, as an optional action, to remove a standing request for auto-merge from its own project rules, which the core rule now repeats (the consuming project of the extraction and this repository have one in section 9 of their entry file since 2026-11-03; this task removes this repository's). Needs 3.11 first. Verified by guard tests (auto-merge refused into the production branch and on release branches), by the adapter's tests of `host protect` and the workflow against a fake host, by bootstrap tests for the three cases (protectable, not protectable, no admin rights) and for the switch, by the conflict script on a fixture of a squash merge, and by the CORE scan. The owner's decision of 2026-11-03.
