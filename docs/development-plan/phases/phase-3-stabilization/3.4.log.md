### 2026-11-04 — the loader, the checks, the migration step, the guide
- **Branch:** `feature/3.4-local-adapters` — done.
- **What was built:** (1) `tools/lib/local-adapters.mjs` loads `harness-adapters/<axis>/<name>/` into the registries of the adapters (`STACKS`, `ADAPTER_RUNTIMES`, `HOSTS`) under `local:<name>`; the command line, `guard-shell`, `format-edited` and the session start call it before they read the profile, and the generators of a local runtime join the managed files. (2) `frameworkAdapters` (lock) keeps local names out of the lock and out of the files a sync takes; the migration guard lets the fix of a rejected adapter stay in the working tree; the commit of the migration holds it, so `harness rollback` restores it. (3) `harness check adapters` holds local manifests and the `local:` names of the profile file; the new check `local-adapters` (in `check all`) runs the suite on every local adapter; `harness migrate` runs it after regenerating and stops before the commit, naming the adapter, the failed checks and the notes of the versions taken. The rule map and the CORE scan read local adapters too. (4) `core/contracts/new-adapter.md` and the procedure `new-adapter` offer both ways and say how to send a local adapter upstream; design §5 and the new §5.1 describe it.
- **Verified by:** `tests/local-adapters.test.mjs` (a fixture project bootstrapped from this tree, its stack switched to a copy of the node-ts preset kept in `harness-adapters/`: `check all` passes; a sync leaves the folder and the lock free of it; a version that adds a required stack role stops the migration with the adapter and the role named, nothing committed; the fix finishes it in one commit; `harness rollback` gives back the starting commit exactly), and `tools/lib/local-adapters.test.mjs`.
- **Decisions / deviations from the plan:** the profile names a local adapter `local:<name>` (the owner's words in the task), not `local:harness-adapters/<axis>/<name>` as design §5 had it; the folder is found by the axis the name is listed under. A local adapter must import nothing from the framework's tools by a relative path, because the suite runs it from a copy of the framework (the presets import `tools/lib/lock.mjs`; the skeleton imports nothing): written in the guide and the procedure. The suite check of `check all` runs each adapter in a process of its own, so a broken one cannot take the check down. `.prettierignore` gained `.claude/worktrees`, because the local gate's format check failed on the settings files of other sessions' worktrees.
- **Problems / blockers / findings:** `harness init` and `harness adopt` select presets only; bootstrapping a project with `--stack local:<name>` is not built (a project bootstraps with the nearest preset and switches the profile file). Said in design §5.1 and the guide; it is a candidate for the backlog if the owner wants it.
