### 2026-11-03 — exceptions, the report path, and development versions
- **Branch:** `feature/3.8-core-exceptions` — done. The claim was opened first; the branch started from `feature/3.7-pinned-core-scan`, since 3.8 builds on the scan of 3.7, and took `develop` in once 3.7 was merged.
- **What was built:**
  - **(1) Exceptions.** `terms.exceptions` of the profile file (schema, `profile/roles.md`): a list of `{ file, word, report, version }`. In a vendored core, `frameworkCoreProblems` accepts a hit whose file and word (case-insensitive) match an exception whose `version` is the lock's. An exception for another version, or for a hit that is gone, is a problem of its own, so after a sync to the next version the check fails on it (and on the hit, when the word is still there). The hit message of 3.7 now names the exception as the way to wait for a fix.
  - **(2) The report path.** The issue template `.github/ISSUE_TEMPLATE/word-in-core.md` and the README section "A word found in `core/`": a confirmed leak is a defect and a task of the open-ended phase, fixed in a patch release; an ordinary word is answered with `terms.productGeneric` and `core/vocabulary.json`; the framework does not rename its own words.
  - **(3) Development versions.** `harness release --dev` on a release branch sets only `<x.y.z>-dev.<n>` (n from the existing tags), leaving the changelog and its fragments; the release procedure and the releasing guide tag it before the final `harness release`. A tag must hold a `framework.json` whose version is the tag's (the sync checks it), which is why the command exists and the tag is not made by hand.
- **Decisions / deviations from the plan:**
  - An exception names the file as the scan prints it (`harness/core/...`), not relative to the core folder, so it can be copied from the message.
  - Exceptions apply to the vendored copy only: a folder the project owns can be edited, so a hit there is fixed, not excepted.
  - `harness release --dev` is not in the task text; without it the development tag cannot satisfy the sync's version check.
- **Verified by:** unit tests of the exception rules (accepted at its version, stale at another, stale when the hit is gone, not applied outside a vendored folder); a pinned fixture project (`tools/lib/project-checks.test.mjs`) whose exception passes `check core` at `0.1.0` and fails after the lock moves to `0.1.1`, with the hit reported again, and with only the stale exception once the word is gone; tests of `release --dev` and of the numbering by tags; `tests/leak-report.test.mjs` for the issue template, the README rule and the release procedure's step.
- **Not done here:** the migration note that tells a consumer about the exception and the template is task 3.11 (its first note describes 3.7 and 3.8).
