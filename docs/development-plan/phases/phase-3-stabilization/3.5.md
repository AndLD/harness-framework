# 3.5 — `harness sync` generates the managed files with the tools of the old version

**Status:** ✅ · **Agent:** C2 · **Size:** 2 SP · **Log:** [3.5.log.md](./3.5.log.md)

**`harness sync` generates the managed files with the tools of the old version**: after a sync to a new version `harness check generated` can still fail (a stale skill) until `harness sync --local` runs again, because the first run generates with the tools already in memory. The fix (the owner's decision of 2026-11-03, with 3.11 and 3.12): `sync` only places the new version's files and updates the lock, and a second command, `harness migrate`, runs in a new process with the new version's tools: it runs the migration scripts of 3.12 and regenerates the managed files. `sync` ends by starting it; a consumer whose old `sync` cannot start it (every version before this task) runs `harness migrate` itself, as the migration notes of 3.11 and the procedure `update-framework` say. Verified by a test that syncs a project from one version to a next in which a procedure changed, and passes `check generated` after `sync` alone, and after `sync` of the old version followed by `migrate`. Found in task 17.16 of the project this framework was extracted from.
