### 2026-11-02 — the examples, and the product-knowledge skeleton in every new project
- **Branch:** `feature/1.4-examples` — done. The claim was opened first.
- **Decisions / deviations from the plan:**
  - **The skeleton is a scaffold template, not read from `examples/`.** The design said the bootstrap takes the skeleton from `examples/product/`, but a vendored copy and the template repository hold no `examples/` (design §1.1, and
    `skeleton.test.mjs` says so), so a project bootstrapped from either would have none. The empty skeleton is `core/templates/scaffold/product-{index,glossary,register,backlog}.md`, written by `scaffold.json` to `docs/product/`;
    `examples/product/` is the same skeleton filled for the fictitious project. The design (§6.3) says so.
  - **The profile defaults** (`profile/starter.json`) gain `productKnowledge` (root and specification `docs/product`, the glossary, register and backlog file names, the register and backlog excluded from the scan) and the roles
    `documents.specification` and `documents.glossary`; the entry file's reading map gets a row for the specification. A new project therefore runs `harness check product-knowledge` from the start.
  - **The sample plan is not written into a new project**: a fictitious phase in a real plan would be wrong; it is a reference in `examples/plan/`.
  - **Examples are held by a test** (`tests/examples.test.mjs`): the profile passes `check profile`, the specification passes `check product-knowledge`, the plan passes `plan summary --check` with its index current.
  - **Not done: the other bindings.** The design (§6.3) also mentioned the bindings of the plan, the phases and the code review as coming with the examples. No check needs them, and the profile has no document role for two of them,
    so they are left out; the design says so. A project writes them when the method asks for a value it holds.
- **Problems / blockers / findings:** none that block. An existing project that bootstraps again gets the skeleton files as new files; `harness adopt` keeps a project's own files and adds the missing ones, so an adopted project that has `docs/product/` of its own keeps it.

- **Verify with:** `npm run docs:check`; `npm test` (403 tests); `npm run lint`
