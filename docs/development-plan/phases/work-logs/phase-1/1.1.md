### 2026-11-02 — `harness adopt` for a repository that copied the first harness
- **Branch:** `feature/1.1-harness-adopt` — done. The claim was opened first. Opened from a session of the repository this framework was extracted from, with the owner's authorisation to push here.
- **Decisions / deviations from the plan:**
  - **One engine.** `adopt` is the bootstrap with `adopt: true`, not a second engine: an existing scaffolded file is kept instead of refused (the entry file, the README), the Git part is only `core.hooksPath`
    (no commit, no branch: the project has its own history), and the closing steps differ. `tools/lib/adopt.mjs` is the command (find and validate the old profile file, ask for what it lacks, analyse the scripts,
    run the engine, report); `tools/lib/adopt-steps.mjs` holds the steps that read the project's files.
  - **The entry file.** A project's own rules text is never touched. The managed blocks it lacks are added at the end under one heading, with the markers, and the sync fills them; the project removes its own duplicates in
    its pull request. (Rewriting the project's text to place the blocks would be guesswork.)
  - **What the framework replaces** is decided by `REPLACED_SCRIPTS` (the names the first harness used, from the history of the repository it came from: link, plan, release, gate, coverage, product-knowledge, hook and
    profile scripts, the two Git hooks) and by comparing a script's exported names with the framework's modules (two names in common, or its only one), which finds a renamed copy. Names that say nothing (`main`, `run`,
    `default`) do not count. Nothing is deleted.
  - **Project checks:** a script `scripts/check-*.mjs` that is not replaced goes to `checks.project` (`node scripts/<name>`), so `harness check all` runs it; a failing one fails the adoption (tested).
  - **Runtime configuration.** A new optional runtime role, `hook-adoption` (`adoptConfiguration({ root, profile }) → { files, notes }`), in the contract, the manifest schema and the Claude Code preset: it adds the
    framework's hook entries and deny rules to the project's own `.claude/settings.json` and notes each hook command that is the project's own. Cursor gets the role with its preset (task 1.2).
  - **Validation first.** The old profile file must be valid for the schema of this version; the whole of it is validated before anything is written or moved (a key of an older format fails the adoption and is named,
    the project left as it was; tested). Migrating older formats is not part of the task.
  - **A message of the engine** that the `--self` test pinned ("Kept the files of the framework itself") is kept for that mode; adopt says "Kept the project's own files".
- **Problems / blockers / findings:**
  - A project that adopts from a folder (the default, the running framework) gets a lock whose source is that folder; a real adoption passes `--from <Git URL> --to <version>`. The README row says `--from`.
  - The adopted project gets the scaffold files it lacks (plan index, stack file, changelog, workflows, …) in its working tree, as a bootstrap does; the report lists those it kept. A project may not want all of them: it removes them in its pull request.
  - The conformance suite does not check the new role (it is optional and needs a runtime-specific file); the check that logic roles export their functions covers its presence.
