### 2026-11-04 — `sync` places the files, `migrate` brings the project to them
- **Branch:** `feature/3.5-migrate` — done, started from `develop`.
- **What was built:** `sync` (not `--local`) no longer generates the managed files: it replaces `harness/`, rewrites the lock (the record of the managed files stays as it was until they are regenerated) and then starts `node harness/tools/harness.mjs migrate` of the new tree in a new process (`startVendoredMigrate`, a seam `startMigrate` for tests; a tree with no command line has nothing to start). The new command `harness migrate` (`tools/lib/migrate.mjs`) regenerates the managed files with the tools that run it. A failing migration fails the sync with the way to run it again, the files and the lock staying in place. The bootstrap still generates in its own process (nothing was synced before it). `sync --local` is unchanged (it is how a change of the profile file is applied). README and design §1 say so.
- **Decisions / deviations from the plan:** `migrate` is only the regeneration for now; the migration scripts, their record in the lock and the printing of the notes are task 3.12, which extends the same command. A consumer's old `sync` cannot start `migrate`, so the first sync after it (every version before `0.2.0`) is followed by `migrate` by hand; the note of `0.2.0` says so (written by the release).
- **Verified by:** `tools/lib/migrate.test.mjs` on two copies of this tree as versions `1.0.0` and `1.1.0` (a procedure, and so a generated skill, changed): `sync` alone leaves `check generated` passing when run with the project's vendored tools; a sync that starts nothing (an old consumer) leaves it failing, and `migrate` run by the project's tools fixes it; a failing migration fails the sync with the message; `npm test`, lint, typecheck, `npm run docs:check`.
- **Problems / blockers / findings:** none.
- **Next step:** task 3.12 (migration scripts, run in order, and the migration test); it needs this one.
