### 2026-11-03 — migration notes, their shape, their areas, and the release that requires them
- **Branch:** `feature/3.11-migration-notes` — done. The claim was opened first; the branch started from `feature/3.8-core-exceptions` (the first note describes 3.7 and 3.8) and took `develop` in once 3.8 was merged.
- **What was built:**
  - **(1) The notes.** `migrations/<version>.md` in a fixed shape (title, "What changed for a project", "Areas touched", "Required actions", "Optional actions", "How to verify"); `migrations/README.md` describes the shape and the rule that a mechanical change is a migration script (3.12), not an instruction. `migrations` is in `framework.json`'s `distributable`, so a project that skips versions finds every note in its vendored copy.
  - **(2) The release refuses a version without its note.** `release.migrations` of the profile file (a new optional role; the framework's own profile sets it) names the folder. `harness release` (dry run too) stops when the note is missing or has the wrong shape, and writes the note's areas and a "Migration note:" link under the version's heading of the changelog. The release procedure, the releasing guide and the profile document say so; the procedure's paragraph is conditional on the role. A development version (`release --dev`) needs no note.
  - **(3) Areas.** `migrations/areas.json` is the fixed list: area names, each with globs, and an `ignore` list (tests). `harness release` takes the files that changed in `core/`, `tools/`, `adapters/` and `profile/` between the tag of the previous release (from the changelog's links) and the working tree, assigns each to the first area whose glob matches, and writes the list between two markers of the note. A changed file that no area claims stops the release, and a test requires that every file the framework has today is claimed and that no area is stale.
  - **(4) The note of `0.1.1`:** what the scan of 3.7 means for a project, the vocabulary, the exceptions and the issue template of 3.8, the development versions, the notes themselves. Required: regenerate the managed files (`sync --local`, since the `release` procedure changed and a sync generates with the old tools, task 3.5), and clear what `check core` reports. Optional: `release.migrations`, trying a development tag.
  - **(5) The README** has a section, "Taking a version", for taking one version or several in order.
- **Decisions / deviations from the plan:**
  - The requirement is a profile role, `release.migrations`, not unconditional, since `harness release` also serves the releases of every project that uses the framework; only the framework's own profile sets it here.
  - The areas are written by the release, between markers, so the note's author never types them.
  - The Git rules area also holds the Git hooks and the guards; the broad `checks` area is last, so a file belongs there only when no narrower area claims it.
- **Verified by:** `harness release --dry-run` on a scratch `release/0.1.1` branch: it fails without the note and with it lists `procedures, profile file, core vocabulary, checks` for the changes since `v0.1.0`; `tools/lib/migration-notes.test.mjs` (shape, areas, markers, the real `areas.json` and the real notes); a fixture project in `tools/lib/project-checks.test.mjs` (refused without the note and with a wrong shape, the areas derived from the diff since a tag, the changelog link, no note for a development version); `npm run docs:check` (the CORE scan included).
- **Problems / blockers / findings:** none. The migration scripts (3.12) and the probe areas (3.15) will read `areas.json`.
