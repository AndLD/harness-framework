### 2026-11-05 — the usage role, the estimate, the gate and the samples
- **Branch:** `feature/5.6-usage-gate` — built, branched from `develop` as it is on the remote.
- **What was built:** (1) The runtime contract gains the **optional** role `usage` (`usageFor(profile) → { means, read(), plans, subscriptions, defaultModel }`, schema `logic-optional`): the means to read the
  account's windows and a table of coefficients (percent of the 5-hour and the weekly window per SP, by subscription, model family and step kind; money on an API key). Claude Code reads the windows by the
  desktop app's `get_usage` (or asks the owner on the command line) and has Pro, Max 5x, Max 20x and the API; Cursor asks the owner and has a mock subscription; the skeleton has a red `usage.mjs`; the
  conformance suite checks the role where it is filled and skips it where it is not. (2) `tools/lib/flow-usage.mjs`: the estimate of a step, the subscription (the flow's setting, else `usage.subscription` of the
  ignored local profile file, else the plan the reading names), the gate `gateStep` (GO, WAIT until a reset, STOP, ASK), the fit of a step in a window, and the samples of `usage.jsonl` (written, read, and the
  difference between a step's end and start, cut when a window reset in between). (3) `harness flow estimate <n>`, `gate <n> <step>` and `sample <n> <event> [<step>]`
  (`tools/lib/flow-usage-command.mjs`); `flow dispatch` adds the estimate, the means to read the usage, the gate and the samples; `flow check` flags a step that cannot fit one window where the subscription
  is known and a bad line of `usage.jsonl` (`flow-usage-check.mjs`). (4) The flow settings `usage` gain `safetyFactor` (1.2) and `maxWaitMinutes` (300) and are merged one level deeper than the others (a flow that
  sets only its subscription kept no thresholds before). (5) The runtime contract, the plan method (section 10), the procedure `run-flow` (step 3, step 5), the flow and flow-log templates, the new-adapter guide,
  the design, the README and a changelog fragment.
- **Verified by:** `flow-usage.test.mjs` (the estimate per subscription, model and kind; the gate under, over, with a window that reset between the reading and the step, a step that fits no empty window,
  no reading, no estimate, the API's cost; the fit; the sample writer and reader; the measured use with a cut window); `flow-usage-command.test.mjs` (the commands through `flowCommand`, the check, `dispatch`);
  the adapters' tests; the conformance suite on both presets and on broken copies (no way to read, a bad unit, a zero coefficient; a runtime without the role is skipped); `npm test`, `npm run test:coverage`,
  `npm run lint`, `npm run typecheck`, `npm run docs:check`.
- **The probe:** a scratch flow with one 5 SP step on Pro, with the **real reading of the account** (Pro, 5-hour 26% resetting at 12:30Z, weekly 7%) at 08:50Z: `harness flow gate` answered WAIT until 12:30Z ("with 72% to
  come it passes 85%; it resets in 221 minutes"); at 12:31Z, after the reset, the same reading answered GO. A 4 SP step (57.6% with the factor) fit at once. `flow sample` wrote a `step-start` and a `step-end`
  line and printed the measured use, cutting the 5-hour window that reset between them.
- **Decisions / deviations from the plan:** (a) **The role is optional, so it is a minor addition** (design §1.4: a minor version adds a role with a default); the default is the framework's manual usage, which
  asks the owner. It changes no contract that an existing adapter meets, so it needs no major version and no owner approval of a contract change. (b) **The coefficients are provisional.** No flow has run on a
  measured account yet, so the numbers of the table are a first estimate from the plan's own scale (1 SP is about one focused agent session; Opus 1.7 times Sonnet, Haiku a third; Max 5x and 20x scale the Pro
  figures down) and are marked `provisional` in the table and in the output of the tools; task 5.7 replaces them from `usage.jsonl`. (c) **WAIT versus STOP** is decided by `usage.maxWaitMinutes` (300, the
  length of the 5-hour window): a 5-hour reset is waited for, a weekly one stops the flow for the owner. (d) **The subscription is not known in CI**, since the local profile file is ignored, so `flow check` flags
  a step that does not fit only where a flow's setting or the local file names the subscription; `flow estimate` shows all. (e) The Est. usage column stays the planner's figure in percent of the weekly
  window; the gate uses the table, not the column.
- **Problems / blockers / findings:** (1) `usageFor` first returned the module's own table, so a caller that changed it changed the next one: it returns a copy. (2) The flows' `usage` setting was merged
  one level only, so `{ "usage": { "subscription": "pro" } }` dropped `stopAt`: fixed in `parseFlow`. (3) The desktop app reports the plan's name (`Pro`) in the reading, which the tools map to a subscription id.
- **Next step:** task 5.7, `harness flow calibrate`, which reads `flows/usage.jsonl` and proposes new coefficients for this table.
- **Verify with:** `npm test`, `npm run docs:check`, `node tools/harness.mjs adapter test adapters/runtime/claude-code`, `node --test tools/lib/flow-usage.test.mjs tools/lib/flow-usage-command.test.mjs`.
