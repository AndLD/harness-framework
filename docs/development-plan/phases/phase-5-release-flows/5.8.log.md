### 2026-11-05 — external repositories in a flow
- **Branch:** `feature/5.8-cross-repo` — branched from `develop` (tasks 5.6 and 5.7 were merged by then; `develop` was merged into it once, with two documentation conflicts kept on both sides).
- **What was built:** (1) `tools/lib/flow-repos.mjs`: the `repos` setting as rows — the home repository is implicit, an external one is `{ remote, role, kinds }` under an alias (kinds default to `consumer-take`; only
  `consumer-take` and `custom` may run in an external repository) —, the checks of the rows and of a step against them (its repo is a row, its kind is allowed there, its scope names no task or phase id of the other plan),
  the folders on this machine from `repos.<alias>` of the ignored `harness-profile.local.json`, and the words of a prompt. (2) The Repo column is optional: a step table without it, or an empty cell, is the home repository;
  the flow template leaves it out and says how to add it. (3) `harness flow status` checks an external `consumer-take` through the host: the lock the repository holds (done when it names the version) and its pull requests
  that mention the version (an open one is running; a merged one the lock does not show yet is said), the host being the new optional role `remote-state` (`remoteFile`, `remotePullRequests`; the GitHub preset reads them with
  `gh`, in `adapters/host/github/remote.mjs`). (4) The prompt: a new section `external` sends the worker to that repository's own entry file and approvals and tells it to name the work by what it did; the header loses
  the home repository's entry file for an external step and the Repository line for the home one. (5) `harness flow dispatch` starts the worker in the folder from the local file, and falls back to the manual executor,
  with a note, when the folder is not set. (6) The procedure `run-flow` (a section "Other repositories": the orchestrator only starts a worker, edits nothing, and the authority of 5.3 covers the home repository only), the
  procedures `release` and `triage-reports` (home repository only), the plan method §10, the host contract, the new-adapter guide, the design, the flow template and the step prompts, a changelog fragment.
- **Verified by:** `flow-repos.test.mjs` (the rows, the folders, the settings and step problems, the prompt words), `flow-status.test.mjs` (the lock and the pull requests of an external step: done, running, not started, a merged
  pull request the lock does not show, an unreadable one, and the home repository never asking the host), `remote.test.mjs` (the file and the pull requests through the `gh` seam), `flow-repos-command.test.mjs` (status, prompt,
  dispatch with and without the folder, the check, and a flow with no Repo column), the existing flow tests adapted to the new shape; `npm test`, `npm run test:coverage`, `npm run lint`, `npm run typecheck`, `npm run docs:check`.
- **Decisions / deviations from the plan:** (a) **The host reads the other repository** by a new optional host role, `remote-state` (a minor addition, design §1.4: a role with a fallback — a step in a repository the host cannot read
  keeps the State column's mark and the status says so). The task says "through the host (its pull requests, its lock file)"; the host contract had nothing for it. (b) **The old `repos` shape is gone**: 5.4 wrote it as a map
  of aliases to paths, which only its own tests used; an alias is now a row, a path in it is refused with a pointer to the local file. No project had a flow yet. (c) **Only `consumer-take` and `custom` run in an
  external repository**; a `cut` and a `triage-fix` are the home repository's by 5.3, and a `tasks` step names task ids, which belong to the plan that holds them. (d) The check refuses any task or phase id in the scope
  of an external step, so the "never by the consumer's task ids" rule is held by the tool and not only by the wording.
- **Problems / blockers / findings:** the external step of 5.9 is where this is exercised against a real consumer; here the host was a seam and the `gh` calls were tested through theirs, not against GitHub.
