### 2026-11-04 — a flow cuts releases and answers reports at its levels; waits for the owner's approval
- **Branch:** `feature/5.3-flow-authority` — done, waiting for the owner's approval in the pull request (a change of the meaning of core rules). Branched from `feature/5.2-flows` while #88 was open; after its squash merge the pull request was retargeted to `develop` and `harness branch update --previous feature/5.2-flows` brought it in.
- **What was built:** (1) the Git rule `agent.ask-merge` lets the orchestrator of a flow the owner started approve the merges of a release or a hotfix when the cut's level is below the flow's `askAt` or the flow is seamless: by merge commit once the required checks are green, never by auto-merge or an administrator's bypass, tagged, logged as a decision. (2) The procedure `release`, step 4 and "When a flow cuts": the orchestrator reviews the migration note by the unbiased analysis (its own list of changes from the fragments and the plan first), sends an incomplete note back, merges, tags, logs. (3) The report rules (`intake-auto`, `intake-notify`) and the procedure `triage-reports` let such a flow approve answers and closings at their level (D4 by default); creating a report stays the owner's. (4) The releasing guide (scaffold and this repository), `run-flow` (what the entry file keeps for the owner, except cuts and answers at their levels), the plan index of this repository and design §11. (5) The rule-to-check map: `agent.ask-merge` is now "partly" held, by the runtime adapter's `guard-shell` (auto-merge refused on a release or hotfix pull request, so a flow's cut is merged by hand) and the host's ruleset (the required checks before a release merges, so no cut on a red check).
- **Verified by:** the guard's tests (`adapters/host/github/merge-guard.test.mjs`: auto-merge on a release or hotfix pull request is still refused), the conformance suite of both adapters whose manifests changed, `npm test`, `npm run docs:check`, lint. **Probe** (a subagent on a scratch project, a brainstorm flow with the default levels and the `manual` executor, steps: tasks, the cut of `1.0.0-dev.1`, the final `1.0.0`): in the first run the orchestrator reviewed the migration note against its own list from the changelog fragments, found a breaking rename the note left out, and sent the note back instead of cutting; in the second run, with the corrected note, it cut `1.0.0-dev.1` itself (D1, below the default `askAt` D2: the tag on the release branch, nothing merged, no auto-merge, no bypass) and handed the final `1.0.0` to a worker to prepare, stopping before the merges and the tag for the owner (D3). Its log entries say where it read the worker's recommendation before its own analysis (it read the report file whole); the procedure now asks for the recommendations last, and the order still depends on the orchestrator's discipline.
- **Decisions / deviations from the plan:** a seamless flow decides a cut at any level, as `run-flow` says of seamless mode; brainstorm only below `askAt`. The PR title has no `!`: the project is below 1.0, so the version stays the minor `0.3.0` the plan names; the owner decides that with the approval.
