Append-only log of this task, used to resume it in a new session (method, section 6). Write an entry whenever a session ends or pauses, or
the task finishes; commit it in the same pull request as the work. Decisions that concern the whole phase go to the phase's work log (`log.md`). A finished task writes only this log: its "next step" names what follows.

## Entries

### 2026-11-04 — flows, their templates, the procedure `run-flow`, the resume phrases and the design
- **Branch:** `feature/5.2-flows` — done.
- **What was built:** (1) the optional profile role `paths.flows` (schema, roles table; only with `paths.releases`), set here to `docs/development-plan/flows`. (2) The templates `core/plan/flow-template.md` (the `Releases:` and `Needs:` line, a settings block in JSON with every default, the steps table `# | Kind | Repo | Scope | Needs | Stops for | SP | Est. usage | Model | State`), `flow-log-template.md` (running, step started and ended, decision with the own analysis before the worker's recommendation, stop with the digest) and `flows-index-template.md`, plus the scaffold template of the index; the plan method gets section 10. (3) `tools/lib/flows.mjs`: `harness plan summary` creates the index of the folder when the role is set, writes its table (flow, releases, mode, size, estimated usage, status worked out from the steps) and adds a link to it to the releases block of the plan index; its check reports a stale table, a flow file without its parts, a release that two flows declare and one that the releases file lacks. (4) The procedure `run-flow` (auto, so a skill): levels D0 to D4, brainstorm and seamless, the hard limits, "what the entry file keeps for the owner stays the owner's", claim, state check, usage, executors and reuse, the step report, the unbiased analysis, escalation, one pull request per step, restarts, digests. (5) The resume phrases "Run flow N", "Run flows N–M", "Continue flow N" in the profile and the plan index, and the Git rules `agent.plan-approval` and `agent.plan-related` name flows. (6) The design, section 12; method section 7 names the orchestrator of a flow.
- **Verified by:** `tools/lib/flows.test.mjs` (the reading, the status, the problems, the table, the summary that creates and writes the index and links it, the check, the role without a releases file); `npm run docs:check` (CORE scan 0, the generated skill, links, paths); lint; `npm test`. **Probes** on two scratch projects (a filled flow with the `manual` executor, a step report with a D1 and a D2 question, the owner's words "Continue flow 1"), each run by a subagent that read only the scratch folder: in **brainstorm** the orchestrator decided the D1 question, asked at the D2 one (step set to ⏸, a digest with both picks and its recommendation); in **seamless** it decided both, moved the task in the releases file in the same change, logged "review later", and stopped at the final cut, which the entry file keeps for the owner until 5.3. In both, each decision entry has the orchestrator's own pick written before the worker's, and where they differed (both times) the entry answers the worker's argument.
- **Decisions / deviations from the plan:** the procedure is `auto` (like `start-task`: an owner's phrase starts it; its description says "when the owner asks"). The flows index is written by `harness plan summary` (with only the staleness and release checks); the deeper checks stay in 5.4. Before 5.3 a flow's phrase approves no cut and no answer: the procedure stops for anything the entry file keeps for the owner, whatever the mode. Est. usage is in percent of the weekly window (5.6 refines it).
- **Problems / blockers / findings:** the probes ran as subagents, not as sessions started in the scratch folder (the harness-review method's way), so they did not load a scratch entry file or hook; they were told to read only the folder. The brainstorm probe was cut twice by an API error after its decision entries, and wrote the rest of its log when resumed. The seamless probe found that a "running" entry could not tell whether its session had stopped; the procedure now says a claim holds until a "stop" entry follows it. Both probes noticed that a release in no flow will not run (the deferred task's `1.1.0`), as the method says.
- **Next step:** task 5.3 (the authority of a flow: release cuts and answers to reports at their levels), which needs the owner's approval in its pull request.
