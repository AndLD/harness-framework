# 5.4 — `harness flow`: check, status, next and prompt

**Status:** ⬜ · **Agent:** C2 · **Size:** 8 SP · **Needs:** 5.2

**`harness flow`: check, status, next and prompt**: (1) `harness flow check`, part of `check all`: the parts of a flow file and of its log; step ids unique, an inserted step with a suffix; the ids a step names exist (tasks and issues, never a backlog item); a release declared by at most one flow and present in `releases.md`; the `Needs` of steps and of flows resolve and point backwards; the flows index agrees with the files (written by `harness plan summary`). (2) `harness flow status <n>` recomputes the state of each step from the repository, not from the State column, which is only a cache: a `tasks` step is done when its ids are ✅ and their pull requests merged, a `cut` when its tag exists, a `consumer-take` when the consumer's lock names the version (an external repository through the host, 5.8); it compares that with the State column and the newest log entry, and prints the mismatches and the next step, so an orchestrator that stopped in the middle of a step resumes from the truth. (3) `harness flow next <n>` prints the next step and its prompt; `harness flow prompt <n> <step>` renders the prompt of a step from its kind and scope: the standard wording (the claim, auto-merge, branching from the previous task's branch while its pull request is open, where to stop, the step report of 5.2) is written once in the template, and a `custom` step carries its own text. (4) The session-start hook names a flow in progress and its next step. The checks are pure functions with the seams as parameters (the host's command line, the file system root). Verified by a test for each check with a planted defect, by `status` on fixtures (a step done but marked pending; a step left in progress by an orchestrator that stopped), by the rendering of each step kind, and by `npm test`, lint, typecheck and the coverage gate.
