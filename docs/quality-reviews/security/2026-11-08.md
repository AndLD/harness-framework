# Security Review — 2026-11-08

**Type:** full (S1 to S4; S5 and S6 do not apply) · **Commit reviewed:** `18db780` (integration branch) · **Reviewer:** the worker of step 5 of flow 4, an agent session (Claude Opus 5.5) that did not write the tools under review; it is the same kind of agent that did, and no person with security expertise has checked this report · **Previous report:** none · **Catalogue:** the probes of `core/reviews/security/probes/` at the commit reviewed (after 0.5.0, tasks 2.8 and 2.9)

> The framework holds no secret and runs no service, so the first review found nothing critical, but it **fails its gate on S4, the agent harness**. The largest risk is that a session on this public repository can read text written by outsiders while it holds the owner's full credential, with no rule that calls that text data and no sandbox. The largest strength is the host's ruleset on the two protected branches, with a job token that is read-only by default, no stored secrets and a single development dependency.

Open 🟠 findings are recorded at the level of a component, as section 7 of the method requires on a public repository.

## 6. Strengths (keep list)

- The ruleset of the host holds the production and the integration branch: no direct push, no force-push, no deletion, required checks; the bypass is only for merging a pull request.
- A sync refuses a tag that moved since it was first seen (`tools/lib/source.mjs`).
- The default job token is read-only, workflows cannot approve pull requests, no secret is stored on the host, and no workflow runs a fork's code with privileges.
- Text an outsider writes is passed to CI scripts through variables, never spliced in (`check security` defends this).
- The hooks run without a shell (`execFile`, `spawnSync` with a list of arguments).
- One development dependency, locked, with no install script; plain Node at run time.
- The secret scan works on a planted value, and 14 scriptable probes have a check.

### 🟠 High

#### S-20261108-01 — The context added at the start of a session holds text written by outsiders

- **Dimension:** S4 · **Probe:** S4-011 · **Effort:** S · **Status:** new · **Outcome:** fix
- **Evidence:** the session-start hook, in its lines about the reports of users. Details are not recorded here (the method, section 7).
- **Impact:** text that anyone can write on the public repository reaches every new session as trusted context, with the owner's credential in reach.
- **Fix:** the hook gives counts and numbers only; the text is read when a triage asks for it, under S-20261108-02.

#### S-20261108-02 — No rule says that outside text is data

- **Dimension:** S4 · **Probe:** S4-007 (and S4-008, S4-021, S4-024) · **Effort:** S · **Status:** new · **Outcome:** rule candidate, fix
- **Evidence:** `AGENTS.md`, the method and the procedure `triage-reports` hold no such rule; only the security review's own method says it, for the reviewer.
- **Impact:** an agent that works the reports, pages or tool output has only its own judgement between a planted instruction and an action.
- **Fix:** a rule of core, loaded by every agent, then a planted payload as a test (task 2.10 decides the rule).

#### S-20261108-03 — The agent holds the owner's credential, and no host-side gate stands between it and a merge to production

- **Dimension:** S4 (and S1, S3) · **Probe:** S4-016, S4-010, S4-020, S1-018, S3-011, S3-012, S3-016 · **Effort:** M · **Status:** new · **Outcome:** fix, rule candidate
- **Evidence:** the identity agents use, the ruleset and the absence of an ownership file; the guards that limit the agent are its own hooks. Details are not recorded here (the method, section 7).
- **Impact:** one mistaken or manipulated session can do what the owner can on the repository; the rules that forbid it are held on the agent's side.
- **Fix:** a separate identity for agents, limited to this repository and without the administrator's role; an ownership file over the CI, hooks and rules; the owner's approval required on the production branch.

#### S-20261108-04 — A session combines private data, outside text and a way out, with no sandbox

- **Dimension:** S4 (and S1) · **Probe:** S4-005, S4-003, S4-004, S4-006, S1-015 · **Effort:** M · **Status:** new · **Outcome:** fix
- **Evidence:** the shared settings of the runtime have no sandbox and bind only the file tools; the services an account connects are not listed per project. Details are not recorded here (the method, section 7).
- **Impact:** with S-20261108-01 or -02, a session can be led to send local data out.
- **Fix:** the runtime's sandbox with a list of hosts, in the preset; triage in a session without write tools.

## 9. The method itself

Each item is in the issue [I-37](../../development-plan/issues/I-37.md).

- **A check narrower than its probe.** S3-001's check accepts any declared `permissions:`, and the probe asks for read-only at the top and write per job: it passed two workflows that fail. Change the check.
- **A check that reads less than the probe.** `settings-audit` reads the shared file only, and S4-002 and S4-023 are about the rules in force. Change the check.
- **A step that did not work.** The result of `check security` with findings does not list the gaps, which step 4 of the procedure relies on: the 14 above come from the work log of task 2.2.
- **Unclear.** The trait `releases` does not separate a project that builds an artifact from one that releases a tag and notes, so S2-020 reads as applying where it cannot. Add the trait or a line to the probe.
- **Did not apply as written.** The method says to work on a branch named after the review date, and a first review is a task with a branch of its own (`docs/2.4-…`). Say that a task's branch name wins.
- **Could be scripted.** S3-016 is `manual`, and part of it (the scopes of the token in use) can be read by a command.
- **Missing.** No probe asks whether the context a *hook* adds has been checked for outside text at the source of the list (S4-011 names the rule; a scriptable companion would have found this), and the report template has no place for the traits (they went into section 2). Add both.

## 10. Verdict and recommended order of work

The framework is not exposed by what it stores; it is exposed by what its agents may do on a public repository. In order:

1. Stop outside text at the door: S-20261108-01, -02 (S, S), then 2.10's rule.
2. Turn on what the host offers for free, the owner's settings: S-20261108-08, -10 (S, S).
3. Bound the agent: S-20261108-03, -04 (M, M), then -09, -14 (S, S).
4. Harden the CI and the release: S-20261108-06 (decision below), -05, -07, -12.
5. Turn `checks.security` on, then the rest: S-20261108-11, -13.

**Open decision: the pins (S-20261108-06).** Recommendation: pin them, in one pull request that changes the templates and the stacks' CI jobs, with a migration note. Until then `checks.security` stays off.
